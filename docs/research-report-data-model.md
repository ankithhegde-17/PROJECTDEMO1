# Canonical Research Report Data Model

Status: Conceptual design, version 1 — consistency reviewed

This is the shared language between the research form, the Next.js server route, n8n, the scoring logic, and the dashboard. It describes what data means before we decide how to encode it in TypeScript or validate it with Zod.

The models were defined progressively and are now reviewed as one end-to-end contract. This document remains conceptual: it defines meaning, ownership, lineage, and scoring boundaries before implementation types are written.

## 1. ResearchRequest

### What we are building

`ResearchRequest` is the small, clean object created when a founder submits the research form. It tells the system what to investigate. It is not a report and it should not contain any research findings.

### Why we need it

It gives every downstream system one predictable input. The frontend does not need to know how n8n researches an idea, and n8n does not need to interpret arbitrary form shapes. This is the first contract in the product.

### Where it belongs

Research form → Next.js server API route → n8n webhook → input validation and normalization.

### Conceptual fields

| Field | Meaning | Data type | Required? | Example | Classification | Needs source? | Conceptual n8n owner | Contributes to score? |
|---|---|---|---:|---|---|---:|---|---:|
| `idea` | The founder’s original startup hypothesis. | Text | Yes | `An AI platform that helps college students discover and apply for internships.` | Observed: supplied by user | No | Validate input | No |
| `targetMarket` | Geography to research. The user may leave it blank. | Text or empty | No | `India` | Observed when supplied; assumed only if the system later fills it | No | Normalize input | Indirectly |
| `targetCustomer` | Initial customer group, if known. | Text or empty | No | `Final-year engineering students` | Observed when supplied; assumed only if later inferred | No | Normalize input | Indirectly |
| `researchDepth` | The amount of research the user requests. Version 1 has two choices: Quick and Standard. | Fixed choice | Yes | `Standard` | Observed: supplied by user | No | Validate input | No |
| `requestId` | A technical ID allowing the application to trace one request through logs and n8n. | Text identifier | Generated by system | `req_01J...` | System metadata | No | API boundary | No |
| `submittedAt` | Time at which the request entered the application. | Date and time | Generated by system | `2026-09-11T10:30:00Z` | Observed system event | No | API boundary | No |

### Important decision

We will never silently turn a missing market or customer into a claim. For example, if the user does not choose a country, n8n may use India as a working assumption, but that assumption must appear in the final report.

## 2. ResearchReport: the outer structure

### What we are building

`ResearchReport` is the single structured result returned by n8n and rendered by the dashboard. Think of it as a folder with named sections, not one long AI answer. Each analytical section has its own internal model below.

### Why we need it

One stable report structure prevents mismatches between systems. The dashboard can render a section confidently because it always knows where to find it. It also lets the workflow return a partial but honest report if one research branch fails.

### Where it belongs

n8n aggregation → output validation → Next.js API response → results dashboard. Later, the same object can be stored as a report record in Supabase.

### Top-level sections

| Section | Meaning | Required in MVP? | Main classification | Source requirement | Conceptual n8n owner | Scoring relationship |
|---|---|---:|---|---:|---|---|
| `meta` | Report identity, timestamps, and workflow, prompt, schema, scoring, and confidence version information. | Yes | System metadata | No | Report assembly | None |
| `request` | The sanitized `ResearchRequest` that produced this report. | Yes | Observed + derived | No | Input validation | None |
| `startup` | Normalized description of the startup hypothesis. | Yes | Inferred, observed, assumed | Only for factual claims | Idea understanding | Provides context |
| `executiveSummary` | Short evidence-referenced synthesis of what was found. | Yes | Inferred | Must reference supporting report records and evidence | Report synthesis | Explains, does not calculate |
| `opportunityScore` | Overall score, dimension scores, confidence, and explanations. | Yes | Derived + inferred explanation | Evidence required for inputs | Deterministic scoring | Final result |
| `problem` | Evidence and analysis of the problem being solved. | Yes | Observed, derived, inferred | Yes for factual claims | Problem branch | Problem severity |
| `customers` | Customer segments, pain points, and buying signals. | Yes | Observed, derived, inferred | Yes for factual claims | Customer branch | Customer evidence |
| `market` | Market trends, metrics, sizing evidence, and uncertainty. | Yes | Observed, derived, inferred, assumed | Yes for claims and metrics | Market branch | Market and growth dimensions |
| `competitors` | Structured records for direct and indirect competitors. | Yes | Observed + inferred | Yes | Competitor branch | Competitive opportunity |
| `competitorMatrix` | Feature-by-feature comparison across competitors. | Yes | Observed + derived | Inherited from competitor sources | Deterministic metrics | Competitive opportunity |
| `competitiveGaps` | Evidence-backed ways the product may differ meaningfully. | Yes | Inferred | Yes | Gap analysis | Competitive opportunity |
| `businessModel` | Analysis containing plausible monetization candidates, comparisons, and the model recommended for validation. | Yes | Inferred + observed signals | Yes for signals | Strategy branch | Monetization potential |
| `mvp` | Focused version-one product recommendation. | Yes | Inferred | Evidence links where available | Strategy branch | None |
| `risks` | Risks, their severity, and possible mitigation. | Yes | Observed, derived, inferred | Yes for factual claims | Risk branch | May feed one natural dimension; informs confidence and verdict |
| `validationExperiments` | Practical tests of the biggest uncertainties. | Yes | Inferred | Links to evidence or assumptions being tested | Validation planner | None |
| `recommendation` | Verdict, reasons, and next actions. | Yes | Inferred | Grounded in report evidence | Report synthesis | Interprets score and risks |
| `evidence` | One deduplicated library of reusable evidence items used across report sections. | Yes | Observed, derived, inferred | Observed evidence must resolve to sources; derived and inferred evidence must preserve lineage | Evidence aggregation | Score and confidence inputs |
| `sources` | One deduplicated library of all sources used. | Yes | Observed + derived metadata | Each source is itself the attribution record | Source collection | Confidence inputs |
| `assumptions` | Explicit working assumptions used anywhere in the report. | Yes | Assumed | No, although supporting context may exist | Every branch, aggregated | Reduces confidence |
| `limitations` | Known gaps, failures, or uncertainty in the research. | Yes | Derived + inferred | No | Quality review | Reduces confidence |

### The report’s central rule

The report has one evidence library and one source library. Analytical records reference `evidenceId` values, and observed evidence resolves to `sourceId` values. The UI can then label a statement as data, derived result, AI insight, or assumption without guessing.

### Report metadata

The `meta` record contains only technical provenance: `reportId`, `generatedAt`, `researchVersion`, `reportSchemaVersion`, `workflowVersion`, `promptVersions`, `scoringVersion`, and `confidenceVersion`. These values make a report reproducible and debuggable; they are not research evidence and never affect opportunity scores.

### Report-wide structural rules

1. Every required top-level section remains present, including in a partial report. A failed or incomplete branch returns its section with empty lists, explicit unavailable values, and linked `Limitation` records rather than omitting the section.
2. Required lists use an empty list when no records exist. An empty list means “no records were produced,” not “the researched concept does not exist.” The reason must be recoverable from limitations or coverage metadata.
3. All identifiers are globally unique within a report and use a type prefix such as `ev_`, `src_`, `segment_`, or `risk_`.
4. References point from the consuming record to the record that owns the information. Raw URLs appear only in `Source`.
5. A summary may not introduce a new factual claim. `executiveSummary` therefore contains summary text plus `relatedRecordIds` and `evidenceIds` that trace its material statements to existing analysis.

## What you should understand before the next section

A data model is a contract, not a database table and not a user-interface design. It sets the meaning and expected shape of information as it crosses system boundaries. The request is deliberately small because its job is to start research; the report is broad because its job is to communicate a completed investigation.

## 3. Shared research foundations

The next four models are the evidence system for the whole product. They let a market statistic, a competitor price, a customer complaint, and an AI interpretation all be represented honestly and reused across the report.

### 3.1 Source

#### What it represents

A `Source` is the original place where research material came from: for example, a government dataset, a university study, a competitor pricing page, a reputable news article, or a Reddit discussion. It records the source once in the report-wide source library.

#### Why the system needs it

The source record answers, “Where did this information come from?” Keeping it separate prevents repeated URLs, keeps attribution consistent, and makes it possible to assess whether a source is suitable for the claim being made.

#### Where it enters the pipeline

Search and web-collection branches discover raw pages or datasets. The source-collection stage cleans their metadata, removes duplicates, assigns a simple source category, and adds each usable source to the library before evidence extraction.

#### Sections that reference it

`Source` records are referenced by `EvidenceItem` records. Those evidence items are then reused by problem, customer, market, competitor, competitive-gap, business-model, risk, scoring, recommendation, and validation sections.

#### Conceptual fields

| Field | Meaning | Conceptual data type | Required? | Example value | Classification | Requires source attribution? | n8n stage |
|---|---|---|---:|---|---|---:|---|
| `sourceId` | Stable identifier used elsewhere in the report. | Identifier | Yes | `src_014` | System metadata | No | Source collection |
| `url` | Canonical web address, if the source is online. | Web address or empty | Usually | `https://example.com/pricing` | Observed | No | Source collection |
| `title` | Title shown by the original source. | Text | Yes | `Pricing Plans \| Internshala` | Observed | No | Source extraction |
| `publisher` | Organization or person responsible for the source. | Text or empty | Usually | `Internshala` | Observed | No | Source extraction |
| `publishedDate` | Date the source was published or last updated, when available. | Date or empty | No | `2026-04-10` | Observed | No | Source extraction |
| `accessedAt` | When our system read the source. | Date and time | Yes | `2026-09-11T10:30:00Z` | System metadata | No | Source collection |
| `sourceCategory` | Plain-language type of source. | Fixed category | Yes | `official_company_source` | Derived classification | No | Source classification |
| `defaultQualityLevel` | Broad default assessment of the source before considering a specific claim. | High / Medium / Low | Yes | `High` | Derived classification | No | Source classification |
| `defaultQualityReason` | Short explanation of the default quality assessment. | Text | Yes | `Official pricing page; appropriate for current product pricing.` | Derived explanation | No | Source classification |
| `relevantTopics` | Areas of the report this source may support. | List of labels | Yes | `competitors, pricing` | Derived classification | No | Evidence extraction |
| `retrievalStatus` | Whether the source was fully accessible and usable. | Fixed status | Yes | `usable` | System metadata | No | Source collection |

`url` is allowed to be empty only for a source such as a manually entered interview note or a public dataset with a non-web identifier. In the MVP, most sources will be web pages. Source quality is only a default: claim-specific suitability is assessed on the `EvidenceItem`. An official company page may be strong evidence for its current price and weak evidence for its claimed customer outcomes.

### 3.2 EvidenceItem

#### What it represents

An `EvidenceItem` is one reusable unit of support or analytical lineage for a claim. It contains an observed fact, a deterministic result derived from evidence, or an AI inference grounded in evidence. Assumptions remain separate `Assumption` records.

For example, “Competitor A lists a free plan” is an evidence item. “Students may expect a freemium option” is an AI insight that can reference that evidence item alongside other evidence.

#### Why the system needs it

Evidence items create a clean boundary between raw source material and AI interpretation. The system can calculate metrics from them, link several report sections to the same support, and show the user what actually backs a conclusion.

#### Where it enters the pipeline

Evidence extraction happens after source collection and before specialized analysis. The extractor reads useful source material and converts it into normalized statements, metrics, quotations, or structured competitor attributes. Later stages may create derived evidence items from those observed items.

#### Sections that reference it

Every analytical section references evidence items. A single item may support the market analysis, a score dimension, and the final recommendation without being copied into each one.

#### Conceptual fields

| Field | Meaning | Conceptual data type | Required? | Example value | Classification | Requires source attribution? | n8n stage |
|---|---|---|---:|---|---|---:|---|
| `evidenceId` | Stable identifier used by report sections. | Identifier | Yes | `ev_082` | System metadata | No | Evidence aggregation |
| `claim` | Short, atomic statement that the evidence supports. | Text | Yes | `Internshala offers a free plan for students.` | Observed, derived, or inferred | Yes for observed; inherited support for derived/inferred | Evidence extraction or metrics |
| `evidenceType` | Whether the item is observed, derived, or inferred. | Fixed category | Yes | `observed` | Classification | Depends on type | Evidence aggregation |
| `sourceIds` | Source records that directly support or qualify the item. | List of identifiers | Yes; non-empty for observed evidence | `src_014` | System metadata | Yes for observed factual claims | Evidence aggregation |
| `inputEvidenceIds` | Earlier evidence items used to calculate or infer this item. | List of identifiers | Yes; non-empty for derived or inferred evidence | `ev_080, ev_081` | System metadata | Provides inherited lineage | Metrics or analysis stage |
| `analysisMethod` | Concise description of the deterministic calculation or inference method. | Text or empty | Required for derived or inferred evidence | `Median of five observed monthly prices.` | Derived explanation | Inherited through input evidence | Metrics or analysis stage |
| `supportingText` | Relevant excerpt or concise extracted detail from the source. | Text or empty | Usually for qualitative evidence | `Free plan available for students.` | Observed | Yes | Evidence extraction |
| `metric` | Name of the quantitative measure, when the item contains one. | Text or empty | No | `starting monthly price` | Observed or derived | Yes or inherited | Evidence extraction / metrics |
| `value` | Numeric or text value attached to the metric. | Number, text, or empty | No | `499` | Observed or derived | Yes or inherited | Evidence extraction / metrics |
| `unit` | Unit needed to interpret a numeric value. | Text or empty | No | `INR per month` | Observed or derived | Yes or inherited | Evidence extraction / metrics |
| `timeframe` | Period the evidence applies to, when relevant. | Text, date range, or empty | No | `2026 pricing page` | Observed or derived | Yes or inherited | Evidence extraction |
| `topicTags` | Labels used to retrieve evidence for a report section. | List of labels | Yes | `competitor, pricing, freemium` | Derived classification | No | Evidence normalization |
| `confidence` | How reliable and complete this evidence item appears. | Low / Medium / High | Yes | `High` | Derived assessment | No | Evidence quality review |
| `confidenceReason` | Why the confidence is at that level. | Text | Yes | `Directly stated on the current official pricing page.` | Derived explanation | No | Evidence quality review |
| `conflictStatus` | Whether the sources agree, disagree, or are insufficient. | Agree / Mixed / Conflict / Unknown | Yes | `Agree` | Derived assessment | No | Evidence aggregation |
| `relatedEvidenceIds` | Other evidence items that support, refine, or conflict with this one. | List of identifiers | Yes | `ev_083, ev_084` | System metadata | No | Evidence aggregation |

An evidence item must remain small enough to be checked. “The internship market is huge and growing, and students dislike current tools” is too broad. It should become separate evidence items because it contains several claims that require different sources.

Observed evidence must have at least one source. Derived and inferred evidence must have at least one `inputEvidenceId`; they may also retain relevant `sourceIds` for convenient traceability. A no-source proposition needed to continue the analysis is an `Assumption`, not an evidence item.

### 3.3 Assumption

#### What it represents

An `Assumption` is a working input used because the system needs to continue but reliable evidence or user-provided detail is unavailable. It is not a finding. The report must expose it so a founder can confirm, change, or test it.

#### Why the system needs it

Research often starts with incomplete inputs. Rather than hiding a choice such as launch geography or estimated customer segment, the system records it. That makes later analysis auditable and prevents an assumption from looking like data.

#### Where it enters the pipeline

Assumptions can be created during input normalization, research planning, market sizing, scoring, or report synthesis. The report-assembly stage deduplicates them into one report-wide list.

#### Sections that reference it

Startup profile, customer, market, competitor, business-model, score dimension, MVP, risk, validation experiment, and final recommendation sections may reference an assumption. The same assumption should be stored once and referenced wherever it matters.

#### Conceptual fields

| Field | Meaning | Conceptual data type | Required? | Example value | Classification | Requires source attribution? | n8n stage |
|---|---|---|---:|---|---|---:|---|
| `assumptionId` | Stable identifier used across the report. | Identifier | Yes | `asm_003` | System metadata | No | Assumption aggregation |
| `statement` | What the system is treating as true for this report. | Text | Yes | `The initial launch geography is assumed to be India.` | Assumed | No | Input normalization |
| `reason` | Why the assumption was necessary. | Text | Yes | `The user did not specify a target market.` | Derived explanation | No | Creating stage |
| `dependentSections` | Report sections whose conclusions depend on it. | List of section labels | Yes | `market, competitors, pricing` | Derived mapping | No | Assumption aggregation |
| `importance` | How much this assumption could change the conclusion. | Low / Medium / High | Yes | `High` | Derived assessment | No | Analysis quality review |
| `validationNeeded` | Whether the founder should confirm or test it before acting. | Yes / No | Yes | `Yes` | Derived assessment | No | Analysis quality review |
| `validationSuggestion` | Best practical way to test or confirm it. | Text or empty | Recommended | `Interview ten Indian students and compare their internship-search workflow.` | Inferred recommendation | No | Validation planning |
| `relatedEvidenceIds` | Evidence that provides context, without converting the assumption into a fact. | List of identifiers | Yes | `ev_021` | System metadata | No | Assumption aggregation |

### 3.4 Limitation

#### What it represents

A `Limitation` records a known boundary on the research result: missing data, inaccessible pages, disagreement between credible sources, thin evidence, or a constraint imposed by the requested research depth. It says what the system could not responsibly conclude.

#### Why the system needs it

Absence of evidence is not evidence of absence. A limitation stops the product from presenting an incomplete search as proof that there are no competitors, no pricing pages, or no customer willingness to pay.

#### Where it enters the pipeline

Every collection and analysis branch can create limitations. The final quality-review stage collects, deduplicates, and attaches them to the affected report sections and confidence assessments.

#### Sections that reference it

Limitations are visible in the report-wide limitations section and may be referenced by market sizing, competitor coverage, score dimensions, risks, and final recommendation.

#### Conceptual fields

| Field | Meaning | Conceptual data type | Required? | Example value | Classification | Requires source attribution? | n8n stage |
|---|---|---|---:|---|---|---:|---|
| `limitationId` | Stable identifier used across the report. | Identifier | Yes | `lim_007` | System metadata | No | Quality review |
| `statement` | Clear description of what is missing, uncertain, or constrained. | Text | Yes | `Only four direct competitors could be reliably verified.` | Derived finding | No, though related evidence is useful | Any branch / quality review |
| `affectedSections` | Report sections that should be interpreted with care. | List of section labels | Yes | `competitors, opportunityScore` | Derived mapping | No | Quality review |
| `impact` | How the limitation affects interpretation. | Low / Medium / High | Yes | `Medium` | Derived assessment | No | Quality review |
| `reason` | Why the limitation exists. | Text | Yes | `Several search results lacked accessible product information.` | Observed or derived | No | Any branch |
| `relatedSourceIds` | Sources involved in the limitation, such as conflicting reports. | List of identifiers | Yes | `src_031, src_032` | System metadata | Recommended when relevant | Quality review |
| `relatedEvidenceIds` | Evidence items affected by the limitation. | List of identifiers | Yes | `ev_101, ev_102` | System metadata | No | Quality review |
| `recommendedFollowUp` | Research or validation action that would reduce the uncertainty. | Text or empty | Recommended | `Verify pricing through competitor product demos or direct outreach.` | Inferred recommendation | No | Quality review |

## 4. Evidence connection rules

### One evidence item can reference multiple sources

`EvidenceItem.sourceIds` must support multiple sources. A claim such as “Students repeatedly describe internship discovery as time-consuming” is stronger when it is supported by a survey, interview notes, and several independent community discussions. Storing the claim once with several supporting source IDs avoids duplication.

### Multiple sources and disagreement

Evidence does not need to pretend that sources always agree. Each evidence item has a conflict status:

| Situation | Representation |
|---|---|
| Several sources support the same claim | One evidence item with multiple `sourceIds` and `conflictStatus: Agree`. |
| Sources usefully qualify the claim | One evidence item with multiple `sourceIds`, a careful claim, and `conflictStatus: Mixed`. |
| Credible sources give incompatible figures | Separate evidence items for each figure, linked through `relatedEvidenceIds`, each marked `conflictStatus: Conflict`; add a Limitation. |
| No reliable evidence is found | Do not create an observed fact. Record a Limitation and, only if the workflow must continue, a clearly labeled Assumption. |

### Quantitative and qualitative evidence

Quantitative evidence uses `metric`, `value`, `unit`, and `timeframe`. It may represent a published statistic or a derived value such as median competitor price. Derived metrics must point to the observed evidence used in the calculation.

Qualitative evidence uses `claim` and `supportingText`. This is appropriate for a competitor feature description, a customer complaint, a product review, or a research conclusion. A qualitative item should preserve meaningful context rather than overstate a single quote as universal demand.

### Competitor websites

Official competitor pages are appropriate evidence for their own features, intended customer, positioning, and publicly displayed pricing. They are not strong proof that those features are widely adopted, effective, or liked by customers. For those claims, the system needs independent evidence such as reviews, user research, or credible reporting.

### Customer pain-point evidence

Customer pain points may be supported by surveys, interview notes, app reviews, community discussions, and recurring public complaints. Community sources are useful for language and workflow friction, but they should be treated as low-to-medium quality evidence and should not alone support market-size or willingness-to-pay claims.

### UI labels

The UI label is derived from the canonical record and classification, never from a visual guess:

| UI label | Canonical origin | Meaning |
|---|---|---|
| DATA | `EvidenceItem.evidenceType: Observed` or explicitly user-provided request data | Directly extracted from a source or supplied by the user. |
| DERIVED | `EvidenceItem.evidenceType: Derived` | Calculated deterministically from observed evidence. |
| AI INSIGHT | `EvidenceItem.evidenceType: Inferred` or an evidence-linked analytical interpretation | An interpretation produced from linked evidence. |
| ASSUMPTION | `Assumption` record | A transparent working input used because information is incomplete. |

## 5. MVP source-quality model

The MVP should use a combination of a detailed category and a simple High / Medium / Low quality level. Categories tell the user what a source is; the level tells the system how cautiously to use it. A numeric score would imply false precision before we have calibration data, so we will not use one in version 1.

| Source category | Default quality level | Appropriate use |
|---|---|---|
| Government or regulator | High | Official statistics, legal or regulatory facts, public datasets. |
| Academic research | High | Carefully scoped research findings and methods. |
| Official company source | High for that company’s own facts | Features, pricing, positioning, product announcements. |
| Established industry research | Medium or High | Market trends and market-size context; inspect methodology and recency. |
| Reputable publication | Medium | Reported events, funding, market commentary, company context. |
| News | Medium | Recent developments, subject to recency and reporting quality. |
| Company marketing page | Medium for directly stated company facts | Product claims and positioning; weak for independent performance claims. |
| Community, forum, social source | Low | Customer language, pain points, hypotheses to validate; weak for broad factual claims. |

Choose the category by the page's evidentiary role. Formal product documentation, pricing, filings, and help material use `Official company source`; promotional landing pages and case studies use `Company marketing page`. This keeps the two company categories mutually understandable even when the publisher is the same.

Quality is claim-dependent. An official company pricing page is high quality for that company’s price but poor evidence that the overall market will pay that price. Each Source therefore stores a category, `defaultQualityLevel`, and `defaultQualityReason`; the EvidenceItem confidence assessment then evaluates suitability for the specific claim.

## 6. Assumptions and limitations are different

An assumption is a choice the system makes to proceed. A limitation is a constraint on what the research can establish.

| Question | Assumption | Limitation |
|---|---|---|
| What is it? | A provisional input. | A documented gap or constraint. |
| Example | `Launch geography is assumed to be India.` | `Market sizing could not be verified for India.` |
| Does it drive analysis? | Yes, and affected sections must reference it. | It restricts confidence in analysis. |
| How is it resolved? | Founder confirms it or runs a validation test. | More research, access, or better data reduces it. |
| Can it be presented as fact? | Never. | Never. |

## 7. Architectural review

The design meets the core architectural requirements.

1. Source data is stored once in `sources`; report sections only reference evidence, and evidence references source IDs. URLs and source metadata are not copied into every section.
2. Evidence can be reused. One pricing observation can feed the competitor record, feature matrix, monetization analysis, and opportunity score.
3. AI insights remain distinguishable because inferred evidence and report conclusions must link back to observed or derived evidence IDs. An AI insight without support is treated as an unsupported hypothesis, not a finding.
4. Uncertainty stays visible. Missing evidence becomes a Limitation; a necessary working choice becomes an Assumption; conflicting information is preserved rather than averaged away.
5. The model remains MVP-sized. It has a single source library, a single reusable evidence unit, and plain-language High / Medium / Low source quality—enough structure for trustworthy research without adding a complex knowledge graph.

## What you should understand before the next section

The important pattern is source → evidence → analysis. A source is raw material, evidence is the specific reusable support extracted from it, and analysis is the system’s interpretation. Assumptions and limitations sit alongside that chain so uncertainty stays visible.

## 8. StartupProfile

### What it represents

`StartupProfile` is the system's shared understanding of the startup hypothesis being researched. It turns the founder's unstructured idea into a concise, consistent profile that every research branch can use. It is a description of the hypothesis, not a claim that the startup, market, or customer demand already exists.

### Why the system needs it

The same idea can be described in many ways. For example, “an AI tool for internships” could refer to job discovery, application automation, career coaching, university software, or employer recruiting. A normalized profile gives the market, competitor, customer, and scoring branches a common research target.

### Where it is created

It is created immediately after input validation in the idea-understanding stage. That stage receives the original `ResearchRequest`, separates the user's own input from its normalized interpretation, creates only necessary assumptions, and passes the profile to the research planner.

### Sections that depend on it

The research planner, problem, customers, market, competitors, business models, MVP strategy, risks, validation plan, and final recommendation all depend on it. They use it as context; they must not treat its inferred fields as independent evidence.

### MVP V1 boundary

The MVP needs a focused description, initial user, buyer, and business-type hypotheses, a value proposition, and a core workflow. These hypotheses guide research; later analytical models own validated customer roles and monetization conclusions. V1 does not need a detailed business canvas, persona hierarchy, brand identity, legal entity type, funding stage, or technical architecture.

### Conceptual fields

| Field | Meaning | Conceptual type | Required? | Example | Classification | Evidence requirement | n8n stage |
|---|---|---|---:|---|---|---|---|
| `startupProfileId` | Stable identifier for this normalized profile. | Identifier | Yes | `profile_001` | System metadata | None | Idea understanding |
| `normalizedDescription` | Clear restatement of `request.idea` using consistent language. | Text | Yes | `A student-facing platform that uses AI to discover relevant internships and streamline applications.` | Inferred normalization constrained by user input | None; it must remain faithful to `request.idea` | Idea understanding |
| `conceptName` | A temporary descriptive name used in the report header. | Text | Yes | `AI Internship Discovery Platform` | Inferred | None | Idea understanding |
| `category` | Product category used to guide research. | Text | Yes | `Career discovery and application workflow` | Inferred | None | Idea understanding |
| `industry` | Broad industry context. | Text | Yes | `Education technology and recruitment technology` | Inferred | None | Idea understanding |
| `targetMarket` | Geography or market boundary for research. | Text | Yes | `India` | User-provided when supplied; otherwise assumed | No external source required; an assumption ID is required if not user-provided | Input normalization |
| `targetCustomer` | Primary intended user or customer segment. | Text | Yes | `College students seeking internships` | User-provided, normalized, or assumed | No external source required; assumption ID required when not supplied | Idea understanding |
| `initialUserHypothesis` | Initial view of who would regularly use the product; CustomerAnalysis later owns the researched role. | Text | Yes | `Students` | Inferred from the hypothesis | None | Idea understanding |

### Information-boundary rules

| Information kind | Treatment in StartupProfile |
|---|---|
| User-provided information | Preserve the original wording once in `request.idea`; use explicitly supplied market and customer information directly. |
| Normalized information | Restate for clarity without adding meaning. `normalizedDescription` must be traceable to `request.idea`. When AI performs the restatement it is classified as Inferred; exact preserved user values remain Observed. |
| AI-inferred information | Use for useful research hypotheses such as category, initial buyer, and core workflow; label it as inferred and avoid presenting it as external market fact. |
| Assumptions | Use only where the workflow needs a decision that the user did not provide, such as a launch geography. Link to an Assumption record. |

`conceptName` is deliberately a descriptive label rather than a generated brand. Inventing a polished company name can make an early hypothesis feel more validated than it is.

## 9. ProblemAnalysis

### What it represents

`ProblemAnalysis` describes the customer problem that the startup proposes to address, the groups who experience it, the current ways they cope, the harm or friction it creates, and the strength of the evidence behind the hypothesis.

It does not decide whether the startup will succeed. It answers a narrower question: “Is there meaningful evidence that this problem exists, affects the intended customer, and is painful enough to investigate?”

### Why the system needs it

Founders often start with a solution and assume the problem is important. This model forces the product to separate the proposed solution from evidence that customers actually experience the underlying pain. It also creates the problem-severity input for the opportunity score.

### Where it is created

The problem-research branch gathers problem-specific surveys, reviews, interviews, public discussions, and existing-alternative information. Evidence extraction creates reusable `EvidenceItem` records. The problem-analysis stage groups them, derives score inputs, identifies counter-evidence, and produces this model before the scoring stage.

### Sections that reference it

Customer analysis reuses its pain points; market and competitor analyses provide context on alternatives; the opportunity score uses its scoring inputs; MVP and validation planning use its uncertainties; and the final recommendation explains whether the problem deserves further validation.

### MVP V1 design choice

V1 should classify a small set of highest-priority pain points and supply evidence-backed inputs to the canonical Problem Severity score. It should not create separate overall problem scores, attempt a clinical-style diagnosis, calculate monetary loss without evidence, or claim universal frequency.

### Problem-score inputs

The `ProblemAnalysis` supplies inputs to the opportunity score; it does not let an LLM invent the number. For MVP V1, the deterministic scoring stage should consider:

| Input | Meaning | Classification | Evidence expectation |
|---|---|---|---|

| Workaround burden | Evidence of time, money, effort, delay, or missed opportunity. | Observed or derived | Linked evidence; quantified claims require units |
| Unmet need after alternatives | Extent to which the problem remains inadequately solved after considering current alternatives and counter-evidence. | Derived | Linked alternative and negative-signal evidence |

These are upstream analytical inputs. The canonical Opportunity Scoring V1 rubric later in this document defines their fixed weights. Evidence breadth, assumptions, and limitations affect confidence and coverage caps rather than the attractiveness score itself.

### Information-boundary rules

1. A problem summary is an AI interpretation, so it must link to evidence IDs and must not contain invented statistics.
2. Pain-point severity and frequency are qualitative analytical assessments. The only 0–100 problem number is the canonical `Problem Severity` ScoreDimension produced by deterministic scoring.
3. A reported number belongs in an evidence item. The analysis references it instead of copying its source text repeatedly.
4. A manual workaround may be inferred from repeated descriptions, but it must state its uncertainty when direct confirmation is limited.
5. If the system cannot find reliable evidence for a pain point, it must create a Limitation. It must not give that pain point a high score merely because the proposed solution sounds useful.

## Architectural review for these two models

1. `StartupProfile` is deliberately contextual. It guides research but does not masquerade as evidence about the external world.
2. `ProblemAnalysis` reuses shared source, evidence, assumption, and limitation records. It does not duplicate page URLs, source metadata, or raw quotations.
3. AI-generated content stays traceable: profile classifications identify themselves as inferred, while problem conclusions and signals reference supporting evidence IDs.
4. The Problem Severity dimension remains auditable because it comes from explicit analytical inputs and counter-evidence, while documented uncertainty changes confidence or activates a coverage cap.
5. The MVP avoids over-modeling by using a few high-priority pain points and broad Low/Medium/High confidence rather than pretending to have clinically precise measurement.

## What you should understand before the next section

The profile defines what we are investigating; problem analysis tests whether the underlying customer pain is worth investigating. Neither model is proof that the product should be built. Their job is to create a disciplined basis for the later customer, market, competitor, and scoring sections.

## 10. CustomerAnalysis

### What it represents

`CustomerAnalysis` explains whose problem appears worth solving, what they are trying to achieve, how their needs differ by segment, who would use, buy, or benefit from the product, and what evidence exists for demand and adoption.

It does not repeat pain-point severity, frequency, or workaround burden already owned by `ProblemAnalysis`. Instead, it tests the customer side of the hypothesis: whether identifiable people or organizations appear to have an important job and demonstrate behavior or adoption signals. Payment signals are recorded here as customer evidence, but BusinessModel owns their monetization interpretation and score use.

### Why the system needs it

A broad label such as “students” is too vague to guide a product decision. First-year students, final-year students, parents, colleges, and employers may have different incentives, urgency, budgets, and adoption barriers. This model lets the report distinguish interest from intent and a user from the person who pays.

### Where it is created

The customer-research branch collects surveys, customer interviews, public discussions, reviews, behavioral signals, product reviews, and evidence of current buying or workaround behavior. Evidence extraction produces reusable `EvidenceItem` records. Customer analysis groups that evidence by segment and produces this model. It also links relevant pain points already defined in `ProblemAnalysis` instead of recreating them.

### Sections that depend on it

Market analysis uses segments to establish addressable scope. Competitor analysis uses them to compare targeting and positioning. Business-model analysis uses user, buyer, and beneficiary roles. MVP strategy uses jobs and adoption barriers. The opportunity score uses customer-evidence inputs. Validation planning uses uncertainties and weak signals to propose tests.

### MVP V1 boundary

V1 needs one primary segment, up to three secondary segments, a small set of jobs to be done, customer role clarity, segment-specific pain-point links, current behavior signals, willingness-to-pay signals, adoption barriers, and counter-evidence.

It does not need a detailed persona canvas, demographic segmentation engine, customer-lifetime-value estimate, full buying-committee map, survey sample statistics, or a fabricated willingness-to-pay price. Those can be added after the first grounded research workflow is proven.

The canonical Opportunity Scoring V1 rubric later in this document fixes these four factors and their weights. Willingness-to-pay signals feed Monetization Potential, not Customer Evidence. Evidence breadth, assumptions, and limitations affect confidence and coverage caps.

### Evidence and interpretation rules

1. `CustomerAnalysis` references reusable evidence IDs. It never embeds raw URLs or duplicates the source library.
2. A complaint in a forum can support a hypothesis about customer language or friction, but it cannot by itself establish market-wide demand or willingness to pay.
3. A current workaround proves behavior only to the extent supported by evidence. It does not prove the customer would switch to a new product.
4. Willingness-to-pay must remain a signal. For example, paid resume services may be adjacent evidence but have low transferability to an internship-discovery tool.
5. When buyer identity is uncertain, `customerRoles` must include `Unknown buyer`, an Assumption, or a Limitation. The system must not silently label the product B2C or B2B.
6. The same pain point is referenced from `ProblemAnalysis`; it is not copied and rescored here. CustomerAnalysis adds segment-specific relevance, customer jobs, behavior, and demand evidence.
7. A large possible segment is contextual information for later market analysis. It is not evidence of customer demand in this model.

## Decisions Finalized

1. Customer demand is modeled separately from problem severity. `ProblemAnalysis` owns the core pain; `CustomerAnalysis` owns who experiences it, what they try to achieve, and whether they show demand or adoption signals.
2. Every customer role is explicit: user, buyer, beneficiary, influencer, or unknown buyer. Roles may overlap but uncertainty cannot be hidden.
3. Willingness to pay is represented as evidence-backed signals with transferability, never as an invented monetary estimate.
4. Segment-specific pain points link to `ProblemAnalysis` records instead of duplicating severity, frequency, or workaround burden.
5. Current behavior is valuable evidence of demand but is not equivalent to intent to pay or intent to adopt.
6. Customer Evidence uses segment and job clarity, behavior consistency, segment-specific pain relevance, and adoption readiness or barriers. Willingness-to-pay evidence is reserved for Monetization Potential; assumptions and limitations affect confidence and coverage caps.

## Decisions Still Open

1. The exact rubric for High / Medium / Low job importance, urgency, transferability, and adoption-barrier confidence.
2. Whether V1 should allow manually entered founder interview notes as a distinct source category or wait for a later research-input feature.
3. How many secondary segments the dashboard should display before moving lower-priority ones into an expandable view.

## What I Should Understand

Customer analysis does not ask only, “Do people have this problem?” It asks four different questions: who has it, what outcome they want, what they already do about it, and whether there is credible evidence they would adopt or pay for a better solution. Keeping those questions separate prevents a persuasive AI summary from turning weak interest into fake demand.

## 11. MarketAnalysis

### What it represents

`MarketAnalysis` defines the market boundary relevant to the startup hypothesis, gathers evidence that the market exists, describes relevant trends and quantitative indicators, and records whether market size can be responsibly reported, estimated, or must remain unavailable.

It answers whether the opportunity has enough market evidence to investigate further. It does not forecast company revenue, guarantee market access, or use the largest adjacent category merely to produce an impressive number.

### Why the system needs it

“AI internship platform” can overlap recruitment technology, job boards, internship marketplaces, university career services, education technology, and AI career tools. A market analysis needs an explicit, defensible boundary; otherwise an LLM can attach a large but irrelevant global statistic to a narrow startup hypothesis.

The model also separates market size from growth. A category can be large but stagnant, small but growing, or promising with weak evidence. These distinctions later feed the separate Market Potential and Growth / Trend Strength score dimensions.

### Where it is created

The market-research branch receives the target market, primary customer segment, and category from `StartupProfile`. It retrieves sources, extracts market evidence into reusable `EvidenceItem` records, classifies trends, and validates the geography and timeframe of each metric. Deterministic calculations may produce derived estimates only after their inputs and assumptions have been recorded. A market-analysis stage then creates this model.

### Sections that depend on it

Opportunity scoring uses its Market Potential and Growth / Trend Strength inputs. Competitor analysis uses the defined market boundary and geography. Business-model analysis uses market accessibility and spending context. Risks and validation experiments use limitations and missing inputs. The final recommendation uses the market's attractiveness and confidence without treating either as a success prediction.

### MVP V1 boundary

V1 needs a clear market definition, relevant geography, a short set of supported trends, a few useful metrics, market-sizing records that can honestly be unavailable, counter-signals, limitations, confidence, and transparent scoring inputs.

V1 does not need macroeconomic forecasting, industry valuation, a five-year revenue model, Monte Carlo simulation, complex econometrics, or a numerical SOM based on guessed market share. A numeric SOM is usually unavailable in V1 unless there is unusually strong, specific evidence and a defensible method.

### Market evidence rules

1. A published statistic remains an `EvidenceItem`; a market metric or size estimate references it through evidence IDs rather than copying URLs or citations.
2. A derived metric must list every observed input evidence item, its method, unit, geography, timeframe, and material assumptions.
3. A global figure cannot be used as an India figure unless the report clearly labels it global and separately explains any derived localization assumptions.
4. A trend must name its geography and timeframe. “AI is growing” without a relevant scope is not a valid market trend.
5. Search-result volume, competitor count, and social discussion may support category discovery or a hypothesis, but are not valid market-size evidence by themselves.
6. One market-research report is evidence, not unquestionable truth. Conflicting credible figures remain separate evidence items and create a Limitation; the system does not silently average them.
7. Industry growth does not prove that the startup's narrow segment will grow. `startupRelevance` is an explicit field so that broad trends are interpreted cautiously.
8. When inputs are insufficient, a market-size estimate must use `Unavailable`, explain what is missing, and avoid numerical placeholders.

### Architectural Review

1. **No duplicated source data:** EvidenceItem owns extracted source facts; MarketAnalysis stores only the market-specific organization, interpretation, calculation method, and references needed to render or score the analysis.
2. **No unsupported size calculations:** Every Sourced or Derived market-size record requires evidence IDs. Derived records also require method, units, timeframe, geography, and assumption IDs. Otherwise the record is Unavailable.
3. **No hidden assumptions:** Geography, market boundaries, annual spend, eligibility, and market-access assumptions must use shared Assumption records and appear on every affected estimate.
4. **Geography consistency:** Every metric, trend, and size estimate explicitly states its geography. A mismatch becomes a limitation, not an implied localization.
5. **Timeframe consistency:** Every metric, trend, and estimate carries a timeframe. Comparisons across years cannot be treated as directly comparable without an explanation.
6. **Source disagreement preserved:** Conflicting credible sources remain linked evidence items with a Limitation. The system does not average incompatible definitions, geographies, or periods.
7. **No accidental AI statistics:** AI may explain an estimate or trend only from linked evidence. It may not populate a numeric value unless it is sourced or deterministically calculated from recorded inputs.
8. **MVP-sized model:** The model adds six small supporting record types—market definition, trend, growth indicator, market metric, market-size estimate, and reusable signals. It avoids forecasting and false mathematical precision.

## Decisions Finalized

1. Market size has exactly three honest states: Sourced, Derived, or Unavailable.
2. TAM and SAM may be shown only when credible sourced data or fully documented derived inputs exist. SOM is Unavailable by default in MVP V1.
3. Market definition must state included and excluded scope to prevent broad-category inflation.
4. Market Potential and Growth / Trend Strength remain separate score dimensions.
5. Market confidence remains separate from market attractiveness and is never a probability that the startup will succeed.
6. Every market number carries a geography and timeframe; derived numbers also carry method, inputs, assumptions, and units.
7. Conflicting credible market evidence is preserved and reported as a limitation.

## Decisions Still Open

1. Whether V1 should support a non-monetary TAM or SAM, such as addressable customer count, alongside monetary estimates in the dashboard.
2. The precise threshold for considering an industry-report source sufficiently transparent to support a Sourced estimate.

## What I Should Understand

Market analysis is an evidence-boundary exercise. First define the narrow market the startup actually enters. Then ask what is known about its customers, spending, scale, and change over time. A large adjacent market, a broad technology trend, or a confident-looking dollar figure does not make a startup opportunity attractive unless the evidence actually applies to the chosen customer, geography, and workflow.

## 12. Competitive Intelligence

Competitive intelligence is a connected model with three layers:

Source → EvidenceItem → normalized Competitor records → deterministic CompetitorMatrix and metrics → AI-inferred CompetitiveGap records.

The order matters. The system may not conclude that a gap exists until it has gathered structured competitor facts and compared them against customer problems and jobs.

### 12.1 Competitor

#### What it represents

A `Competitor` is a verified product, service, institution, or customer workaround that overlaps meaningfully with the startup's target customer, job, problem, workflow, or geography. It records observed facts separately from cautious interpretations.

#### Why the system needs it

Competitor paragraphs are hard to compare and easy to hallucinate. Normalized records make it possible to build a feature matrix, inspect pricing coverage, compare target segments, calculate honest comparison metrics, and trace every factual claim to evidence.

#### Where it is created

The competitor-research branch discovers candidates using the `StartupProfile`, `CustomerAnalysis`, and `MarketAnalysis` boundary. Collection and evidence extraction verify usable information. Competitor normalization creates one record for each meaningful candidate, while quality review records what could not be confirmed.

#### Sections that depend on it

`CompetitorMatrix`, `CompetitiveGap`, MarketAnalysis context, business-model analysis, MVP strategy, risks, validation planning, and the Competitive Opportunity score dimension all use these records.

#### Competitor types

| Type | Meaning | Example for an AI internship platform |
|---|---|---|
| Direct competitor | Serves substantially overlapping customers with a similar product category or workflow for the same job. | A student internship discovery platform that recommends roles and supports applications in India. |
| Indirect competitor | Solves an important part of the same customer job through a different product category or workflow. | A general professional-networking platform used by students to find internships. |
| Substitute / workaround | A non-comparable product, service, institution, or manual behavior customers use instead of a dedicated solution. | University placement cells, spreadsheets, peer groups, manual web search. |

Recognition or company size never makes a product a direct competitor. Classification depends on actual overlap in target customer, job/problem, workflow, category, and relevant geography.

#### Strength and weakness rule

Competitor-owned sources can establish their stated features, pricing, intended customer, and positioning claims. They do not establish effectiveness, market leadership, product quality, ease of use, satisfaction, or superior AI performance.

### 12.2 CompetitorMatrix

### 12.3 CompetitiveGap

#### What it represents

A `CompetitiveGap` is a potential unmet customer need or differentiation opportunity inferred from several connected inputs: customer jobs or pain points, normalized competitor records, matrix metrics, competitor positioning, and research limitations.

It is not a claim that “few competitors have feature X.” Low feature coverage is only one input. A meaningful gap also needs evidence that the capability matters to a customer segment and that existing solutions do not already address the need through another workflow, positioning, or substitute.

#### Why the system needs it

This model converts structured competitive data into an explainable strategic hypothesis. It prevents the product from treating feature novelty as value, and it makes counter-evidence and research coverage visible beside any claimed differentiation opportunity.

#### Where it is created

After matrix metrics are calculated, a competitive-analysis stage interprets the structured data alongside `CustomerAnalysis` jobs and segment-pain-point links and `ProblemAnalysis` pain points. It produces only evidence-grounded gap hypotheses. Quality review adds confidence and limitations.

### Competitive Opportunity scoring inputs

These three models prepare inputs for the canonical Competitive Opportunity dimension. They do not calculate a final score and never use “fewer competitors” as a shortcut for opportunity.

|---|---|---|---|
| Customer-need coverage | Whether a meaningful customer job or pain point appears insufficiently addressed. | Derived and inferred | Links to ProblemAnalysis, CustomerAnalysis, and gap evidence |
| Differentiation potential | Whether a proposed difference is relevant, evidence-backed, and potentially defensible. | Derived | Gap rationale, counter-evidence, and confidence |
| Feature and positioning saturation | How common relevant capabilities and messages are among eligible, sufficiently covered competitors. | Derived | Matrix metrics with honest denominators and unknown counts |
| Captureability despite substitutes and switching pressure | Whether the opportunity remains practically capturable after considering alternatives, direct competitor overlap, and switching barriers. | Derived | Competitors, CustomerAnalysis barriers, and gap counter-arguments |

The canonical Opportunity Scoring V1 rubric later in this document fixes these four factors and their weights. Competitor count is context only. Research coverage, source quality, assumptions, and limitations affect confidence and coverage caps.

### Competitive intelligence rules

1. A famous company is included only when the record can explain meaningful overlap with target customer, job, workflow, category, or relevant geography.
2. `Not confirmed` and `Unknown` are never treated as `Confirmed absent` in the matrix or metrics.
3. Feature absence requires reliable direct evidence. In MVP V1, it should be rare; most non-observations remain Not confirmed or Unknown.
4. Pricing stays in its original terms. Any later comparison must preserve currency, billing period, plan scope, geography, and timeframe rather than comparing incomparable figures.
5. Every matrix cell is copied from a normalized competitor feature record. The matrix cannot introduce an AI-generated feature status.
6. Every feature metric preserves numerator, eligible denominator, unknown count, calculation explanation, and confidence.
7. A CompetitiveGap must connect customer need, competitor pattern, and counter-evidence. A low-penetration feature alone is insufficient.
8. No verified competitor found means only that research coverage is limited; it never establishes that no competitor exists.

### Architectural Review

1. **Evidence duplication:** Competitor records, matrix cells, metrics, and gaps store IDs that reference reusable evidence; none duplicates source URLs or raw source metadata.
2. **Unsupported strengths and weaknesses:** These require direct factual evidence, independent evidence, a comparative metric, or an explicit research-coverage statement. The model cannot call a product “best” or “weak” without support.
3. **False feature absence:** The five-status feature model distinguishes Confirmed, Partial, Not confirmed, Confirmed absent, and Unknown. Only Confirmed absent supports an absence claim.
4. **Pricing normalization:** Price-point records preserve original currency, period, plan, geography, and timeframe. The model never compares raw prices without later normalization rules.
5. **Matrix denominators:** Metrics exclude Not confirmed and Unknown from the eligible denominator, expose their count, and explain the calculation.
6. **Irrelevant famous competitors:** Classification rationale makes customer/job/workflow/geography overlap explicit before a competitor enters the model.
7. **Unsupported gaps:** Every gap needs customer links, competitor pattern, metrics, evidence, counter-evidence, assumptions, limitations, and confidence.
8. **Competitor count is not opportunity:** Direct competitor counts are context only. Competitive Opportunity evaluates defensible room for customer-relevant differentiation.
9. **Incomplete research coverage:** The coverage record exposes unverified candidates, inaccessible material, unknown feature cells, pricing coverage, geography coverage, and limitations.
10. **MVP discipline:** The model focuses on target customer, jobs, features, positioning, pricing, coverage, and gaps. It excludes market share, revenue forecasts, funding, SEO, patents, social metrics, and speculative SWOT analysis.

## Decisions Finalized

1. Competitive intelligence follows a fixed order: sources → evidence → normalized competitors → deterministic matrix and metrics → inferred gaps.
2. Competitor type is based on meaningful overlap, not brand recognition or industry adjacency.
3. Feature availability has five states, and non-observation is never treated as absence.
4. Matrix metrics use eligible denominators and report unknown coverage explicitly.
5. Strengths and weaknesses must be evidence-bounded; competitor marketing claims do not prove product quality or customer satisfaction.
6. Competitive gaps are customer-relevant strategic hypotheses, not low-feature-count observations.
7. Competitive Opportunity will assess defensible differentiation potential, not competitor count.
8. A coverage record is included in MVP V1 because incomplete research would otherwise create misleading gaps.

## Decisions Still Open

1. The small default feature taxonomy for the MVP and whether it should vary by startup category.
2. The exact rubric for classifying a competitor as direct versus indirect when geography is only partly overlapping.
3. The precise threshold for “sufficient feature coverage” in a matrix metric.
4. Whether community reviews should be included in V1 as independent competitor evidence or only used for customer pain research.

## What I Should Understand

Competitive intelligence is not a list of company names. It is a chain of evidence. First verify what alternatives offer, whom they serve, and what remains unknown. Then calculate comparison patterns with honest coverage. Only after that can the AI propose a gap—and even then the gap is a hypothesis to validate with customers, not a fact that guarantees differentiation.

## 13. BusinessModel

### What it represents

`BusinessModel` records a small set of plausible ways the startup could create and capture value. Each candidate is a monetization hypothesis connected to customer roles, customer behavior, willingness-to-pay signals, observable competitor pricing, and relevant market context.

It does not claim that a pricing model is proven because it sounds common. It answers a narrower question: “Which model has the strongest available evidence to validate first, and what still needs to be proven?”

### Why the system needs it

The user, buyer, and beneficiary may differ. For example, students may use an internship product while a college pays for it, or students may pay directly for premium application support. Without a structured model, an AI can incorrectly treat user interest as payment intent or silently choose a business model that conflicts with the customer roles already identified.

### Where it is created

The monetization-analysis stage starts after CustomerAnalysis, MarketAnalysis, and Competitive Intelligence are available. It connects existing role mapping, willingness-to-pay signals, adoption barriers, market economic context, and competitor pricing records. It then creates a limited set of candidate models, compares them, and recommends one initial validation hypothesis.

### Sections that depend on it

Opportunity scoring uses its monetization-potential inputs. MVP strategy uses its value-exchange and buyer information. Risks and validation experiments use its barriers and assumptions. The final recommendation uses the recommended model only as a validation priority, not as a finalized commercial plan.

### MVP V1 boundary

V1 needs two or three plausible candidates, evidence-backed value exchange, customer and buyer roles, observable comparable behavior, barriers, assumptions, confidence, and one recommended model to test first.

V1 does not need revenue forecasts, unit economics, customer-lifetime-value estimates, pricing optimization, margin calculations, sales compensation, advertising yield estimates, or a complete financial plan. These would create false precision before customer validation.

### Monetization comparison rules

1. A candidate must identify a payer role. If the buyer is unknown, the candidate may exist only with an explicit Assumption or Limitation; it cannot be marked high confidence.
2. Customer interest, product usage, or a reported pain point are not willingness-to-pay evidence. They may support the value hypothesis but not the payment claim.
3. Comparable competitor prices support what is publicly charged, not proof that the proposed startup can charge the same amount or achieve the same conversion.
4. Adjacent payment behavior must record directness. Paying for interview coaching is not direct proof of paying for internship discovery.
5. `pricingHypothesis` stays a hypothesis. It is never a forecast, recommended final price, or evidence of market willingness to pay.
6. An advertising candidate requires evidence of repeat attention, relevant advertiser demand, and user experience fit. It should not be generated solely because the startup has users.
7. The recommended candidate is the best validation priority under current evidence, not the “correct” permanent business model.

### Monetization Potential score inputs

`BusinessModel` prepares inputs for the canonical Monetization Potential dimension. It does not calculate the final score or forecast revenue.

| Input | Meaning | Classification | Evidence expectation |
|---|---|---|---|
| Buyer clarity | Whether a realistic payer role and segment can be identified. | Derived | Customer-role records and candidate payer references |
| Value-exchange strength | Whether the payer receives a clear, relevant outcome linked to a meaningful job or pain point. | Derived | Customer jobs, ProblemAnalysis pain points, and candidate rationale |
| Payment and comparable evidence | Strength and directness of customer willingness-to-pay signals, competitor pricing, institutional budgets, or other comparable exchanges. | Observed and derived | CustomerAnalysis signal IDs, comparable behavior, competitor pricing, and market evidence |
| Model accessibility after barriers | Practical ability to reach, convert, sell to, or obtain approval from the payer after considering counter-evidence. | Derived | Candidate barriers, negative signals, and market context |

The canonical Opportunity Scoring V1 rubric later in this document fixes these four factors and their weights. Assumptions, limitations, source breadth, and evidence quality affect confidence and coverage caps.

### Architectural Review

1. **No duplicated evidence:** BusinessModel references shared customer roles, jobs, pain points, competitor pricing records, market metrics, and reusable evidence IDs. It does not copy source URLs or rebuild earlier analyses.
2. **No fake payment proof:** Pain, engagement, and a large segment remain separate from willingness to pay. Payment claims require direct or explicitly adjacent comparable behavior.
3. **Buyer uncertainty is visible:** Unknown buyers, assumed payer roles, and weak institutional-budget evidence reduce confidence instead of being turned into a polished B2B or B2C story.
4. **No misleading price comparisons:** Competitor plans remain in their original terms. This model does not normalize currencies, periods, or custom plans into a false price benchmark.
5. **No revenue forecasting:** Candidates describe a value exchange and validation question; they do not predict conversion, revenue, margins, or market share.
6. **Candidate count is limited:** Two or three plausible models prevent the analysis from becoming a generic catalog of every possible monetization mechanism.
7. **Recommendation is conditional:** The first model to validate is selected for evidence quality, accessibility, and learning value, not treated as a permanent business-model decision.

## Decisions Finalized

1. BusinessModel represents a small set of monetization hypotheses, not a proven plan or forecast.
2. Every candidate must identify a payer role, value exchange, supporting behavior, competitor or market context, barriers, assumptions, limitations, and confidence.
3. User, buyer, and beneficiary remain distinct; payment intent cannot be inferred from user interest alone.
4. Willingness-to-pay signals carry a directness label so adjacent paid behavior is not overstated.
5. The recommended model is the first monetization hypothesis to validate, not the final commercial strategy.
6. Monetization Potential uses buyer clarity, value-exchange strength, payment and comparable evidence, and model accessibility or barriers. Uncertainty changes confidence or activates a coverage cap rather than becoming an attractiveness input.

## Decisions Still Open

1. The exact rubric for Direct, Adjacent, and Weak analogy in comparable payment behavior.
2. Whether the dashboard should group candidates by consumer, institutional, and marketplace models when more than two are viable.
3. The maximum number of candidates displayed in a standard-depth report.

## What I Should Understand

A business model is a hypothesis about an exchange: a specific payer gives money or another valuable commitment because the product helps them achieve a valuable outcome. Customer pain is necessary context, but it is not proof that anyone will pay. The goal of this model is to make that uncertainty visible and turn it into the next validation question.

## 14. MVPRecommendation

### What it represents

`MVPRecommendation` describes the smallest product hypothesis worth building or prototyping to test the most important customer value supported by current research. It is not a roadmap for the complete company product.

The recommendation connects a primary customer segment, one core customer job, the highest-priority supported pain points, any meaningful competitive gap, and an optional monetization hypothesis into a narrow end-to-end workflow.

### Why the system needs it

Early-stage product ideas often expand into long feature lists before the founder has tested whether the central value is useful. This model forces every included capability to earn its place by connecting to a customer job, pain point, evidence, or adoption barrier. It also makes deliberate exclusions visible.

### Where it is created

The MVP strategy stage runs after ProblemAnalysis, CustomerAnalysis, Competitive Intelligence, and BusinessModel are available. It uses their IDs and evidence rather than copying their contents. It selects a single testable product hypothesis, defines a minimal workflow, and identifies the metric that should be observed during validation.

### Sections that depend on it

ValidationExperiment owns the experiment design and any success threshold. Risks use the scope to identify product and adoption risks. FinalRecommendation uses the MVP scope as an immediate next action. OpportunityScore does not directly score the number of features in the MVP.

### MVP V1 boundary

V1 needs an explicit MVP target, a value proposition, must-have capabilities, deferred capabilities, a simple core workflow, implementation approach for any AI-dependent capability, and one metric to observe.

Nice-to-have capabilities are useful only when the report needs to distinguish a near-term extension from a deliberately deferred feature. They are optional and should remain short. Three categories—must-have, nice-to-have, and deferred—are retained because they make scope decisions visible without adding product-roadmap complexity.

### Scope and evidence rules

1. Each must-have capability must connect to at least one customer job and one pain point; a competitive gap or adoption barrier link is required when that is the reason for inclusion.
2. A feature without a traceable customer-value reason is excluded or marked Nice-to-have.
3. The core workflow must be end-to-end enough for a customer to experience the promised value, but no broader than necessary to test it.
4. Competitive gaps are optional. The MVP can test a strong customer problem even when no well-supported gap has been found.
5. A monetization candidate is optional in the MVP target. Early testing may first validate value and adoption before payment behavior is tested.
6. AI-dependent capabilities must state the least complex approach that can test the value and a manual or deterministic fallback where practical.
7. Numeric success thresholds do not belong in this model. They are experiment-specific hypotheses owned later by `ValidationExperiment`.
8. The recommendation may not claim speed, accuracy, superiority, placement outcomes, or guaranteed conversion unless such claims have reliable supporting evidence.

### Architectural Review

1. **No duplicate research data:** MVPRecommendation uses IDs to reference customer segments, jobs, pain points, gaps, business-model candidates, evidence, assumptions, and limitations. It does not copy their source data or findings.
2. **No generic feature list:** Every must-have capability has explicit job, pain-point, and evidence links; gaps and adoption barriers are linked when relevant.
3. **No accidental roadmap:** Nice-to-have and deferred lists state scope decisions, but the model does not promise future implementation or attempt to design the full product.
4. **No fabricated success target:** The model owns the metric to observe, while ValidationExperiment later owns test context and success criteria.
5. **AI remains justified:** AI scope is selected for customer value and can be replaced by deterministic or concierge methods during validation.
6. **MVP-sized design:** One target, one core job, one focused workflow, and a small set of must-have capabilities keep the recommendation testable.

## Decisions Finalized

1. MVPRecommendation is a minimal product hypothesis, not a product roadmap.
2. The MVP target references existing segment, job, pain-point, competitive-gap, and business-model records instead of duplicating them.
3. Must-have, Nice-to-have, and Deferred categories remain in V1 because they make scope discipline explicit; Nice-to-have may be empty.
4. Every must-have capability needs traceable customer-value links and evidence or documented assumptions.
5. The MVP metric records what to observe; ValidationExperiment will later own any numeric success threshold.
6. AI-dependent capabilities require a customer-value rationale and an appropriately simple deterministic or manual fallback.

## What I Should Understand

An MVP is not the smallest version of every feature you imagine. It is the smallest complete experience that lets a real customer test one valuable outcome. The feature list matters less than the learning loop: who uses it, what job they try to complete, what pain it addresses, what behavior you observe, and what uncertainty the result reduces.

## 15. Risk

### What it represents

A `Risk` records a startup-specific condition, obstacle, or uncertainty that could materially weaken, invalidate, delay, or obstruct the opportunity if it occurs or proves true. It explains the potential consequence, its evidence basis, its importance, and a possible mitigation.

It is not a generic startup-risk checklist, a prediction of failure, or an enterprise risk-management system. A report should normally contain three to seven material risks, selected because the current research gives a concrete reason they matter for this startup.

### Why the system needs it

Positive signals alone do not show whether an opportunity is worth investigating. A founder also needs to see where the hypothesis could break: customer adoption, market access, differentiation, monetization, execution, data dependencies, regulation, or go-to-market. The risk model turns those concerns into specific, evidence-connected questions for validation.

### Where it is created

Risk analysis runs after the problem, customer, market, competitive-intelligence, business-model, and MVP-recommendation stages. It reuses their evidence, negative signals, adoption barriers, assumptions, limitations, and scope decisions. It creates a risk only when those inputs imply a material potential consequence for the startup hypothesis.

### Sections that depend on it

The dashboard prioritizes material risks. Existing opportunity-score dimensions may consume relevant risk inputs where they naturally belong. MVP strategy and future ValidationExperiment records use risk priority to focus learning. FinalRecommendation later uses the risk register to explain why a founder should proceed, validate, or deprioritize.

### MVP V1 category set

The MVP uses seven practical categories. They are broad enough to cover the main opportunity threats without becoming an enterprise taxonomy.

| Category | Covers |
|---|---|
| Customer / adoption | Trust, need intensity, switching behavior, retention, or willingness to use. |
| Market | Market accessibility, demand context, geographic mismatch, or category constraints. |
| Competitive | Incumbents, substitutes, differentiation, supply control, or switching barriers created by alternatives. |
| Monetization | Buyer uncertainty, price sensitivity, free alternatives, conversion, or procurement constraints. |
| Product / execution | Scope, operational complexity, marketplace dynamics, integrations, or delivery constraints for the MVP. |

### Severity, likelihood, and confidence

These are deliberately different questions.

| Field | Question answered | Example |
|---|---|---|
| Severity | If this happens, how much could it harm the opportunity? | A restriction on handling applicant data could have High severity. |
| Likelihood | Given current evidence, how plausible is it that this will materially affect the startup? | The restriction may have Low or Unknown likelihood for the planned MVP. |
| Confidence | How reliable is our assessment of this risk? | Confidence can be Low if legal requirements have not been researched deeply. |

No percentage probabilities are used in MVP V1. Missing evidence produces `Unknown` likelihood, not Low likelihood.

### Risk priority rule

Priority is a transparent, rule-based ordering label rather than a fake multiplication of Low/Medium/High values.

| Priority | MVP V1 interpretation |
|---|---|
| Critical | High severity and either High likelihood or direct impact on the central MVP hypothesis, with enough evidence to require immediate attention. |
| High | High severity with Medium or Unknown likelihood, or a material threat to the primary customer, value proposition, differentiation, or buyer model that should be validated early. |
| Medium | A meaningful risk with bounded impact, lower likelihood, or a mitigation path that can be tested soon. |
| Low | A relevant but non-material risk for the initial MVP, or one that can wait until the central hypothesis is tested. |

Low confidence does not erase a severe risk. Instead, it usually produces High validation priority and a clear statement that the risk needs investigation.

### Risk creation rules

1. A negative signal becomes a Risk only when its likely consequence could materially affect the startup opportunity. It then references the existing signal or analytical record through `relatedRecordIds` and evidence IDs.
2. A Limitation is not automatically a Risk. A limitation records what research could not establish; a risk records the business consequence if a condition exists or occurs.
3. Evidence-backed risks use observed evidence. Inferred risks must connect evidence to a clear startup-specific consequence. Assumed risks require explicit assumption IDs and cannot be framed with high confidence.
4. A generic statement such as “competition is a risk” is invalid. The risk must identify the specific competitive condition, its relevance to this startup, and the possible consequence.
5. Mitigation is a recommendation for reducing exposure or learning more. It is not evidence that the risk has been solved and does not contain cost, duration, probability, or implementation estimates.
6. The model preserves counter-evidence through `counterEvidenceIds` because one-sided risk reporting creates misleading pessimism.
7. A risk may reference MVP scope or architectural context, such as dependence on external internship listings, but it must identify why that dependency is material and what evidence or assumption supports it.

### Risk versus Limitation

| Concept | Meaning | Example |
|---|---|---|
| Limitation | A boundary on what current research can confidently establish. | `We could not verify whether competitors have access to exclusive internship listings.` |
| Risk | A potential business consequence if a condition is true or occurs. | `If major competitors control exclusive internship supply, a new entrant may struggle to provide comparable opportunity coverage.` |

The risk may reference the limitation. The limitation does not itself prove that the risk will occur.

### Risk versus ValidationExperiment

Risk owns the concern, consequence, evidence, severity, likelihood, confidence, mitigation idea, and validation priority. A future `ValidationExperiment` will own the hypothesis, participant group, test method, metric, success criterion, and expected learning. Risk does not embed a complete experiment.

### Relationship to opportunity scoring

Risk does not create a separate universal score penalty. That would double-count evidence already reflected in the existing score dimensions.

| Risk category | Natural score relationship |
|---|---|
| Customer / adoption | Usually Customer Evidence; Execution Feasibility only when the primary issue is delivery or operation rather than adoption. |
| Market | Usually Market Potential; Growth / Trend Strength only when the primary issue is change over time. |
| Competitive | Can provide inputs to Competitive Opportunity. |
| Monetization | Can provide inputs to Monetization Potential. |
| Product / execution and Technical / data | Can provide inputs to Execution Feasibility. |
| Regulatory / go-to-market | Usually Execution Feasibility, or `None` when it only constrains confidence and recommendation. |

The table identifies likely ownership, not permission to score a risk twice. Each score-relevant risk has exactly one `scoreDimensionKey`. Within that dimension, a ScoreInput references either the risk or its underlying barrier or analytical record as the primary scored basis; it never creates two contributions for the same condition. Other dimensions may cite the risk as context without using it as a score input. Risk then summarizes cross-cutting consequences, affects confidence where appropriate, informs the final recommendation, and prioritizes validation.

### Architectural Review

1. **Startup-specific risks:** Every risk requires a concrete condition, consequence, related records, and evidence or assumptions. Generic checklists are invalid.
2. **Separate concepts:** Severity measures impact, likelihood measures plausibility, and confidence measures reliability of the assessment. They are never interchangeable.
3. **Missing evidence:** Insufficient evidence produces Unknown likelihood or a Limitation, not an artificially low likelihood.
4. **Reusable evidence:** Risk references EvidenceItem IDs and prior analytical records; it never duplicates URLs or source metadata.
5. **Negative-signal reuse:** `relatedRecordIds` links risks to existing negative signals, adoption barriers, competitor gaps, and business-model records rather than creating copies.
6. **Limitation boundary:** A limitation describes missing knowledge; a risk describes potential opportunity harm. They may be linked but remain distinct.
7. **Mitigation boundary:** Mitigations are recommendations and do not claim the risk is resolved.
8. **No arbitrary score penalty:** Risks map to the existing relevant score dimension or confidence assessment, avoiding double counting.
9. **No duplicated evidence effect:** The future scoring model must trace each evidence item to its primary score contribution; the risk register provides interpretation and prioritization around it.
10. **No experiment duplication:** Risk carries only validation priority; detailed tests belong later to ValidationExperiment.
11. **No fake estimates:** The model contains no probability percentages, cost, duration, financial, or engineering-effort estimates.
12. **MVP-sized design:** Seven categories and three to seven material records provide useful coverage without turning the product into enterprise risk management.

## Decisions Finalized

1. Risk uses seven practical MVP categories: Customer / adoption, Market, Competitive, Monetization, Product / execution, Technical / data, and Regulatory / go-to-market.
2. Every risk records severity, likelihood, and confidence as separate Low/Medium/High-style concepts; likelihood may be Unknown.
3. `counterEvidenceIds` is retained in V1 to make risk reasoning balanced.
4. Priority uses transparent rule-based labels, not arithmetic on qualitative labels.
5. Limitations, negative signals, and risks remain different records linked by references where appropriate.
6. Risks do not apply a second arbitrary penalty to the opportunity score; they feed the relevant existing dimension, confidence, recommendation, and validation priority.
7. Mitigations are high-level recommendations, not implementation plans or proof of resolution.

## Decisions Still Open

1. The exact rule for when a High-severity, Unknown-likelihood risk becomes Critical versus High.
2. Whether category-specific dashboard icons or colors are useful enough to standardize in the UI phase.
3. Whether legal or regulatory research needs a dedicated extended-depth mode after the MVP.

## What I Should Understand

Risk analysis is not about listing scary possibilities. It is about making the startup hypothesis testable under uncertainty. A useful risk says what could happen, why that matters here, what evidence supports the concern, what evidence reduces it, and how urgently the founder should learn more. The most dangerous risks are often high-impact risks with weak evidence, because they can quietly invalidate an otherwise attractive plan.

## 16. ValidationExperiment

### What it represents

A `ValidationExperiment` is a recommended practical test that reduces one material uncertainty in the startup hypothesis. It states what is being tested, who should participate, what to observe, how results will be interpreted, and which founder decision the learning should inform.

The initial research report contains recommendations only. It does not contain fabricated experiment outcomes, and a recommended experiment is not evidence.

### Why the system needs it

Research creates a more disciplined hypothesis, but it cannot answer every important question from secondary sources. Validation experiments turn the most material assumptions, limitations, risks, business-model questions, and MVP uncertainties into small learning activities that can happen before expensive building.

### Where it is created

The validation-planning stage runs after all analytical models are available. It selects three to five high-information tests by linking existing uncertainty records to the primary customer segment, MVP scope, and a specific founder decision. It does not execute or track the tests in MVP V1.

### Sections that depend on it

MVPRecommendation may provide the artifact or workflow used in an experiment. Risk provides validation priority for material threats. FinalRecommendation later uses the experiments to identify the founder's next actions. Future experiment results can become EvidenceItems and update the report, but that learning loop is outside MVP V1.

### MVP V1 boundary

V1 recommends three to five prioritized experiments. Each needs a falsifiable hypothesis, target participants, practical method, procedure, experiment-specific metric, outcome decision rules, expected learning, and links to existing uncertainty records.

V1 does not manage recruiting, scheduling, questionnaires, execution logs, participant data, A/B-test infrastructure, dashboards, or results. Its one permitted status is `Recommended`, which makes the pre-execution state explicit without creating an experiment-management system.

### Practical method taxonomy

The MVP uses six method categories. The test focus and procedure distinguish a problem interview from a buyer interview without adding a large taxonomy.

| Method | Appropriate use |
|---|---|
| Interview | Explore customer problems, behavior, buyer role, workflows, willingness to pay, or decision context. |
| Prototype test | Test usability, value proposition, trust, or task completion with a clickable or lightweight prototype. |
| Landing page or fake door | Test interest in a specific proposition or action before building the feature. |
| Concierge or Wizard-of-Oz | Deliver the proposed outcome manually or partly manually to test real value before automation. |
| Pricing or buyer-conversation test | Test payment, budget, procurement, or conversion assumptions with a defined payer. |
| Feasibility test | Test a material data-access, technical, integration, or operational assumption through a limited manual investigation. |

### Hypothesis and participant rules

1. Every hypothesis must be falsifiable and connect a specified customer or buyer context to an expected observable behavior or outcome.
2. “People like the idea” is invalid because it does not identify a behavior, context, or decision.
3. Participants must reference existing CustomerAnalysis segment IDs and an explicit role. “Talk to users” is not sufficient.
4. Buyer tests must use buyer or organizational segments, not only end users, unless the research explicitly identifies the same person as both.
5. Every experiment must link to at least one existing uncertainty record through `relatedRecordIds`. It may link to multiple risks, assumptions, gaps, or MVP capabilities when they share one testable hypothesis.
6. A Limitation should create an experiment only when a founder-run test can meaningfully reduce it. Some limitations instead require better secondary research and should not appear as customer experiments.

### Priority rules

Priority combines materiality and learning value, not uncertainty alone.

| Priority | MVP V1 interpretation |
|---|---|
| High | Tests a central MVP, customer, buyer, differentiation, data, or risk assumption whose answer could materially change the next founder decision. |
| Medium | Produces useful learning but does not block the first MVP or customer test. |
| Low | Relevant later-stage uncertainty that can wait until a more central hypothesis is supported. |

A high-priority risk may have no immediate experiment if its uncertainty cannot be efficiently tested now. Conversely, an experiment can test a valuable assumption even if no Risk record exists.

### Learning-before-building rules

1. Test manually curated recommendations before building an automated recommendation engine.
2. Test a clickable prototype before building full workflow infrastructure.
3. Test data availability with a limited manual collection before building multiple integrations.
4. Test each marketplace side separately before building a two-sided marketplace.
5. Use the simplest artifact that can reveal the needed customer behavior; technical novelty is not a validation goal.

### ValidationExperiment boundaries

| Model | Owns |
|---|---|
| Assumption | A provisional belief the system currently uses. |
| Limitation | A boundary on what current research can establish. |
| Risk | A potential material consequence if a condition occurs or is true. |
| MVPRecommendation | The smallest product experience worth testing. |
| ValidationExperiment | The test method, participants, metric, provisional decision rules, and expected learning. |

An MVP capability may be the artifact in a validation experiment, but the models remain separate. A risk may motivate a test, but no one-to-one mapping is required.

### Relationship to opportunity scoring and future learning

Recommended experiments do not change the opportunity score, because no new evidence has been generated. They can point to weak score inputs, low-confidence dimensions, risks, assumptions, and limitations, but a recommendation is not validation.

The future learning loop remains possible:

Research report → recommended experiment → founder runs test → result captured → new EvidenceItem → report updated → score and confidence recalculated.

MVP V1 stops at the recommended experiment. It does not design the execution, result-capture, or recalculation system.

### Architectural Review

1. **Traceable uncertainty:** Every experiment has `relatedRecordIds` pointing to existing assumptions, limitations, risks, gaps, business-model candidates, MVP capabilities, jobs, pain points, or barriers.
2. **Startup-specific advice:** Hypothesis, participants, artifact, and expected learning are tailored to existing report records rather than generic startup templates.
3. **Falsifiability:** Hypotheses name a target context and observable outcome; outcome criteria include support, weaken, and inconclusive states.
4. **Relevant participants:** Target segment IDs and roles make customer and buyer context explicit.
5. **Observable metrics:** Each experiment metric defines what is counted or observed and how it is collected.
6. **Provisional thresholds:** Success and failure criteria are decision rules for the specific experiment, not claims of universal statistical validity.
7. **Decision-linked learning:** Expected learning states what founder decision becomes easier after the test.
8. **Material priority:** High priority reflects consequence, dependency, weak evidence, and usefulness of learning together.
9. **No duplication:** Existing uncertainty records are referenced, not restated; MVPRecommendation owns product scope, and Risk owns the concern.
10. **No pre-execution evidence:** `Recommended` experiments have no results and do not alter opportunity scores.
11. **MVP focus:** Three to five tests, six practical methods, and one status avoid creating experimentation-management software.
12. **Future-compatible loop:** Successful or failed tests can later create evidence without changing the meaning of this recommendation model.

## Decisions Finalized

1. ValidationExperiment contains recommended tests only, with `status: Recommended`; V1 has no results field.
2. Every experiment traces to existing uncertainty through reusable IDs and does not duplicate underlying analysis.
3. The MVP method taxonomy has six practical categories: Interview, Prototype test, Landing page or fake door, Concierge or Wizard-of-Oz, Pricing or buyer-conversation test, and Feasibility test.
4. Each experiment requires a falsifiable hypothesis, target segment and role, observable metric, provisional outcome criteria, expected learning, and priority.
5. Success criteria, weaken criteria, and inconclusive conditions are explicit decision rules, not universal benchmarks.
6. ValidationExperiment does not alter opportunity scoring until an executed test creates new evidence in a future version.
7. Three to five prioritized experiments keep the report focused on learning before building.

1. The exact default participant count guidance for different methods, which should remain advice rather than a validity claim.

## What I Should Understand

An experiment is useful when it can change a decision. The goal is not to collect positive feedback; it is to expose a material hypothesis to observable behavior and decide what the result means before it happens. Research tells you where uncertainty is. Validation tells you which uncertainty to reduce first, using the smallest credible test.

## 17. FinalRecommendation

### What it represents

`FinalRecommendation` is the final decision layer of the research report. It interprets the research evidence, section analyses, upstream deterministic opportunity score, confidence, risks, assumptions, limitations, and validation priorities to answer: “Is this opportunity worth investigating further, and what should the founder do next?”

It is not a success prediction, investment recommendation, business plan, or new research branch. A positive verdict means the hypothesis deserves further investigation or validation; it does not mean the founder should build a complete startup.

### Why the system needs it

The report contains many useful sections, but founders need a clear decision-oriented synthesis. A score alone cannot account for weak evidence, unresolved buyer assumptions, or a critical data-access risk. The recommendation puts those concerns into an action sequence while preserving the upstream score as authoritative.

### Where it is created

The report-synthesis stage runs only after the score, confidence, risk, and validation-planning stages are complete. It selects and summarizes existing report records. It does not retrieve new sources, create new factual evidence, recalculate scores, alter dimension values, or resolve uncertainty silently.

### Sections that depend on it

The dashboard uses this model as its final decision layer. It references the opportunity score, highest-priority validation experiments, key risks, and selected assumptions and limitations. It also provides the practical order in which a founder should act.

### MVP V1 verdict set

The MVP uses five action-oriented verdicts. This is enough to distinguish a promising opportunity from one needing more evidence without implying a prediction of success.

| Verdict | Meaning |
|---|---|
| Investigate with priority | Current evidence and score support moving quickly into focused validation, while still avoiding full product commitment. |
| Promising — validate critical assumptions | The opportunity has positive signals, but one or more buyer, customer, market, differentiation, or execution uncertainties must be tested before meaningful investment. |
| Mixed — run focused validation | Evidence is balanced or uneven; proceed only with narrow experiments designed to resolve the most decision-changing questions. |
| Deprioritize under current evidence | Current evidence, risks, or constraints do not justify near-term investment relative to other opportunities. This can change if new evidence emerges. |
| Insufficient evidence | Research coverage or consistency is too weak for a responsible directional judgment; conduct targeted research before deciding. |

### Verdict synthesis inputs and rules

The final verdict is not a score-band lookup. Its later deterministic synthesis policy will use these already-finalized model inputs:

| Input | Why it matters |
|---|---|
| Overall opportunity score and dimension scores | Provides the upstream quantitative assessment of attractiveness. |
| Dimension and report confidence | Shows how reliable the score evidence is. |
| Strongest and weakest dimensions | Identifies where the opportunity is supported and where it is fragile. |
| Critical and high-priority risks | Surfaces conditions that could invalidate a promising score. |
| Material assumptions and severe limitations | Prevents a strong narrative from hiding missing data or untested choices. |
| Evidence imbalance or cross-section conflict | Detects cases where one strong section masks weak or contradictory evidence elsewhere. |
| Validation priority | Determines whether the correct action is build-lightly, validate, research further, defer, or reconsider. |

The later verdict policy should be auditable. It may use score bands as one input, but it must allow confidence, critical risks, assumptions, and limitations to moderate the wording. It must not change a score or dimension value to make the narrative more persuasive.

### Recommendation confidence requirements

Recommendation confidence describes how reliable the decision guidance is, not opportunity attractiveness or startup success probability. The canonical confidence framework provides, at minimum:

- Dimension confidence and overall report confidence.
- Source and evidence quality, breadth, agreement, recency, and geographic relevance.
- Cross-section consistency or conflicts.
- Material assumptions and limitations.
- Critical risks with Unknown likelihood or low confidence.

This supports valid combinations such as a promising opportunity with Low recommendation confidence, or a moderate opportunity with High recommendation confidence.

### Model boundaries

| Model | Answers |
|---|---|
| ExecutiveSummary | What did the research find? |
| OpportunityScore | How attractive does the opportunity appear across defined dimensions? |
| FinalRecommendation | Given the score, evidence, uncertainty, risks, and validation priorities, what should the founder do next? |

### No-new-evidence rule

The recommendation stage may select, summarize, compare, interpret, and prioritize existing records. It may not discover facts, introduce statistics, create a new competitor fact, calculate or change score values, hide conflicting evidence, or silently resolve assumptions.

### Architectural Review

1. **Action, not prediction:** The verdict tells the founder what to investigate, validate, defer, or reconsider; it never claims the startup will succeed or fail.
2. **Score remains upstream:** FinalRecommendation references OpportunityScore and relevant dimensions. It cannot calculate a parallel score or override a dimension value.
3. **Not score-only:** Confidence, risks, assumptions, limitations, evidence imbalance, and validation priority moderate verdict wording.
4. **Confidence is separate:** Recommendation confidence describes reliability of guidance and can be low even when attractiveness appears strong.
5. **Reusable signals:** Strongest signals select existing evidence and analysis records rather than creating fresh positive claims.
6. **Selective concerns:** Biggest concerns reference the material subset of risks, negative signals, assumptions, limitations, and weak score dimensions.
7. **Explicit unknowns:** Critical unknowns expose the questions most capable of changing the decision rather than hiding them inside prose.
8. **Referenced next steps:** Next steps use existing ValidationExperiment, MVP, risk, and research-follow-up records; experiment details are not duplicated.
9. **Distinct report roles:** ExecutiveSummary reports findings; FinalRecommendation turns them into decision guidance.
10. **Insufficient evidence is valid:** The verdict can decline to make a directional judgment when confidence and coverage are too weak.
11. **No new facts:** All factual statements trace through existing analytical records and EvidenceItems to Sources.
12. **MVP-sized synthesis:** One verdict, two to four signals, two to four concerns, a few critical unknowns, and three to five next steps keep the decision layer concise.

## Decisions Finalized

1. FinalRecommendation is a decision-oriented synthesis, not a success prediction, investment recommendation, or business plan.
2. MVP V1 has five action-oriented verdicts, including Insufficient evidence.
3. OpportunityScore is upstream and authoritative; FinalRecommendation may interpret but never recalculate or modify it.
4. Verdict wording is moderated by confidence, critical risks, material assumptions, limitations, and evidence imbalance rather than score alone.
5. Strongest signals, biggest concerns, critical unknowns, and next steps use shared IDs and existing evidence; no new evidence is created during synthesis.
6. Critical unknowns are retained as a dedicated field because they clarify which unanswered questions could change the decision.
7. Next steps use a compact action-type set and reference existing validation experiments where possible.

## Decisions Still Open

1. The final auditable verdict policy, including how score bands, confidence, high-priority risks, and severe limitations interact.
2. The exact cross-section consistency checks used to detect evidence imbalance or contradictions.
3. Whether an alternative verdict explanation should be displayed when score and recommendation direction materially diverge.

## What I Should Understand

The opportunity score and the final recommendation answer different questions. The score summarizes attractiveness across a defined rubric. The recommendation tells the founder what to do with that result when uncertainty is real. A promising score with weak buyer evidence should lead to validation, not confident building. A moderate score with strong evidence may still produce a clear decision. The recommendation is useful because it makes that judgment transparent and action-oriented.

## 18. OpportunityScore, ScoreDimension, and Confidence V1

### Assessment-layer purpose

This layer turns the normalized analytical records into an explainable assessment. It preserves the following order:

Research evidence → normalized analytical records → score inputs → deterministic rubrics → dimension scores → weighted overall score → confidence assessment → AI explanation → FinalRecommendation.

The LLM may extract evidence, classify it into the allowed rubric levels, identify counter-evidence, and explain the calculated outcome. It must never choose or alter a final numeric score. Software maps approved rubric levels to values, calculates scores, applies caps, derives confidence labels, and records every calculation input.

### 18.1 Seven dimensions and ownership

The V1 weights are fixed. Each dimension has a clear primary owner and a distinct question.

### 18.2 Scoring primitive

V1 uses a hybrid approach.

Pure direct 0–100 input scores would create false precision because many findings are qualitative. Pure categorical scoring would ignore genuinely useful quantitative data such as a verified addressable population or a confirmed feature-coverage metric. The hybrid keeps both benefits:

1. Analytical stages use sourced or derived quantitative data where it genuinely exists.
2. They classify each scoring input into a defined qualitative rubric level using its evidence.
3. Deterministic software maps the rubric level to a fixed value.
4. Software calculates weighted dimension scores, coverage, caps, overall score, and confidence.

### V1 rubric levels and values

| Rubric level | Fixed value | Meaning |
|---|---:|---|
| Blocking | 0 | Strong evidence indicates the condition materially blocks the opportunity in its current form. |
| Weak | 25 | Available evidence is materially unfavorable or provides little support. |
| Moderate | 50 | Evidence is mixed, limited, or neither clearly favorable nor unfavorable. |
| Strong | 75 | Available evidence is materially favorable and relevant. |
| Very strong | 100 | Multiple relevant findings strongly support the condition, with no material counter-evidence for that input. |
| Unavailable | No numeric value | Evidence is insufficient to classify the input responsibly. |

The values are scoring anchors, not measurements. An input cannot use an arbitrary value such as 67. AI chooses only a rubric level and supplies rationale; deterministic software performs the mapping.

### 18.5 Missing evidence and score caps

Missing evidence is not negative evidence. Each score input can be Assessed or Unavailable.

For an assessed dimension, software calculates a weighted mean using only assessed inputs:

`available input score = sum(numeric value × fixed internal weight) ÷ sum(fixed internal weights for assessed inputs)`

Software also calculates weighted coverage:

`coverage = sum(fixed internal weights for assessed inputs) ÷ 100%`

| Weighted coverage | Dimension treatment |
|---:|---|
| 80–100% | No coverage cap. |
| 60–79% | Score may be calculated, but cannot exceed 80. |
| 40–59% | Score may be calculated, but cannot exceed 65 and is marked coverage-capped. |
| Below 40% | Dimension is Unavailable; no numeric score is emitted. |

Essential-evidence caps apply in addition to coverage caps. They are deliberately few and represent claims that should not be called strong without a basic form of direct support. If more than one cap applies, software uses the lower maximum.

| Dimension | Essential-evidence cap |
|---|---:|
| Problem Severity | No supported target-segment pain point: maximum 50. |
| Customer Evidence | No independent customer evidence or current behavior: maximum 50. |
| Market Potential | No geography-relevant market-existence or addressable-scope evidence: maximum 50. No size/population/spending evidence: maximum 75. |
| Growth / Trend Strength | No relevant current trend: Unavailable. |
| Competitive Opportunity | No verified competitor/substitute plus customer-need link: maximum 50; below required coverage may make the dimension Unavailable. |
| Monetization Potential | Buyer Unknown and no direct willingness-to-pay evidence: maximum 50. |
| Execution Feasibility | Critical dependency unresolved with no manual or concierge feasibility path: maximum 50. |

These caps constrain unjustified extreme claims. They do not turn a potentially attractive but weakly evidenced condition into negative evidence.

### 18.6 Dimension-unavailability and overall-score policy

All seven dimensions are expected, but a score is only meaningful when every dimension can be assessed at a minimum standard.

| Condition | Overall-score policy |
|---|---|
| Every dimension is assessed; all have coverage of at least 60% | Emit numeric overall score with status `Complete`. |
| Every dimension is assessed; one or more dimensions have 40–59% coverage and are coverage-capped | Emit numeric overall score with status `Provisional`. Show capped dimensions and confidence prominently. |
| Any dimension is Unavailable | Overall numeric score is `Unavailable`. Do not redistribute its weight. Show available dimensions, their weights, and the blocking coverage gap. |

Weights are never redistributed. Redistributing would change the meaning of the same overall score between reports and could hide an unavailable critical dimension.

### 18.9 Score bands

Score bands describe attractiveness under the rubric. They are not final verdicts and do not imply probability of success.

| Range | Band | Meaning |
|---:|---|---|
| 0–24 | Weak | Available evidence is materially unfavorable or indicates a likely blocker. |
| 25–44 | Limited | The dimension has weak support or important adverse conditions. |
| 45–64 | Moderate | The dimension is mixed, viable but constrained, or not yet strongly supported. |
| 65–79 | Promising | Available evidence is favorably supportive, subject to displayed confidence. |
| 80–100 | Strong | Available evidence is strongly favorable and sufficiently complete to justify a strong claim. |
| Unavailable | Unavailable | Research is too thin to produce a comparable numeric assessment. |

The top band is `Strong`, not `Very strong`, because pre-launch opportunity research should remain modest even when evidence is favorable.

### 18.10 Overall weighted calculation

When all seven dimensions are assessed, deterministic software calculates:

`overall score = sum(dimension score × fixed overall weight)`

The result is rounded to the nearest whole number only after summing all weighted contributions. Each contribution remains visible to one decimal place for auditability.

For example, a Problem Severity score of 70 contributes `70 × 0.20 = 14.0` points to the overall score. Production code or a deterministic n8n code node performs this calculation; an LLM never does.

### 18.11 Confidence V1 framework

Confidence answers: “How reliable and complete is the research basis for this assessment?” It is not a calibrated probability and must never be presented as the chance that a startup will succeed.

V1 displays only `Low`, `Medium`, and `High`. An internal deterministic checklist may use counts to choose a label, but no numeric confidence percentage is displayed. This avoids false precision while preserving consistent aggregation.

Local `confidence` fields describe the reliability of their owning analytical record. `ScoreDimension.confidence` is the authoritative confidence for a dimension score and is calculated from the dimension-specific checks below. `OpportunityScore.overallConfidence` is the report-level aggregate. `FinalRecommendation.confidence` describes reliability of the action guidance after score confidence and decision-changing risks or unknowns are considered.

### Shared confidence principles

Every dimension evaluates these concepts, with dimension-specific definitions:

| Principle | Meaning |
|---|---|
| Source quality and relevance | Are the sources appropriate for the claim, rather than merely numerous? |
| Evidence breadth and independence | Do multiple independent origins support the finding? Ten reposts of one statistic count as one origin. |
| Directness | Does evidence directly support this exact segment, geography, job, feature, buyer, or dependency? |
| Agreement | Do relevant sources agree, or is the evidence mixed or conflicting? |
| Recency and fit | Is evidence recent enough and matched to the relevant geography and timeframe? |
| Completeness and uncertainty | Are essential inputs available, and how material are assumptions, limitations, and unknown risks? |

Source independence in V1 is assessed by distinct publisher or primary-data origins. Syndicated articles, copied market statistics, and several pages from the same company do not create independent confirmation. This is a practical rule, not a citation graph.

### Confidence-check record

| Field | Meaning | Conceptual type | Required? | Example | Classification | Owner |
|---|---|---|---:|---|---|---|
| `checkKey` | Stable coverage or quality check. | Text | Yes | `customerEvidenceIndependence` | System metadata | Confidence aggregation |
| `label` | Human-readable name of the check. | Text | Yes | `Independent customer evidence` | System metadata | Confidence aggregation |
| `status` | Result of the check. | Strong / Adequate / Weak / Unavailable | Yes | `Adequate` | Deterministic or AI-assisted classification with validation | Confidence aggregation |
| `relatedRecordIds` | Records used to determine the status. | List of identifiers | Yes | `behavior_004, ev_086` | System metadata | Confidence aggregation |
| `rationale` | Why the check has this status. | Text | Yes | `Two independent student sources describe the same recurring behavior.` | AI explanation of evidence | Confidence aggregation |

### Dimension-specific confidence checks

| Dimension | Required confidence checks |
|---|---|
| Problem Severity | Target-segment pain evidence breadth and independence; segment relevance; agreement; recency; alternative/counter-evidence coverage. |
| Customer Evidence | Independent customer evidence; segment and role clarity; behavior directness; adoption-barrier coverage; evidence agreement. |
| Market Potential | Source/method quality; geography and timeframe fit; sizing or population coverage; agreement; market-boundary clarity. |
| Growth / Trend Strength | Trend-source quality; currentness; geography/workflow relevance; independent agreement; counter-trend coverage. |
| Competitive Opportunity | Verified competitor/substitute coverage; feature-cell coverage; geography fit; pricing/positioning coverage; independent evidence and conflicts. |
| Monetization Potential | Buyer clarity; direct payment evidence; comparable-behavior transferability; pricing/budget coverage; barrier and counter-evidence coverage. |
| Execution Feasibility | MVP/concierge-path clarity; critical dependency evidence; data/integration feasibility coverage; regulatory/technical-risk coverage; material unknowns. |

### Dimension confidence aggregation rule

Each required confidence check maps internally to: Strong = 2, Adequate = 1, Weak or Unavailable = 0. This mapping is only a deterministic aid to select a qualitative display label; it is not shown as a percentage.

| Confidence label | Deterministic V1 rule |
|---|---|
| High | At least 80% of required checks are Strong or Adequate, at least half are Strong, no material conflict, and no confidence cap applies. |
| Medium | At least 50% of required checks are Strong or Adequate, no more than one essential check is Weak or Unavailable, and no severe unresolved limitation applies. |
| Low | Any other condition, including insufficient breadth, material conflict, multiple weak essential checks, or a relevant confidence cap. |

### Confidence caps

The following minimal caps prevent a High confidence label when an essential evidence type is missing:

| Dimension | High-confidence cap |
|---|---|
| Problem Severity | Cannot be High without target-segment pain evidence from at least two independent origins or an equivalent strong primary source. |
| Customer Evidence | Cannot be High without independent customer evidence and verified current behavior for the primary segment. |
| Market Potential | Cannot be High with severe geography/timeframe mismatch or unclear sizing methodology. |
| Growth / Trend Strength | Cannot be High without current, relevant evidence from at least two independent origins or one strong authoritative primary source plus corroboration. |
| Competitive Opportunity | Cannot be High when competitor verification or relevant feature coverage is materially incomplete. |
| Monetization Potential | Cannot be High when buyer identity is Unknown or direct payment evidence is absent. |
| Execution Feasibility | Cannot be High when a critical technical, data, regulatory, or operational dependency remains unresolved. |

### Source disagreement and cross-section consistency

`EvidenceItem.conflictStatus` remains visible. Material credible disagreement lowers the relevant confidence check; incompatible figures are never averaged.

The report also performs a small cross-section consistency review:

| Status | Meaning |
|---|---|
| Consistent | Core findings align, or any differences are explained by segment, geography, or timeframe. |
| Mixed | Findings are uneven or qualified, but no direct contradiction changes the main interpretation. |
| Material conflict | Supported analytical records make incompatible claims that could change the opportunity decision. |

A material conflict lowers overall confidence to Low until the report clearly scopes or resolves it. It does not silently rewrite score inputs.

### Overall report confidence

Overall confidence uses the seven dimension confidence labels and report-level checks. It is not a simple average.

1. Convert dimension confidence internally: High = 2, Medium = 1, Low = 0.
2. Calculate a weighted confidence indicator using the same seven overall weights.
3. Apply safeguards: any material cross-section conflict, two or more Low confidence dimensions with weights of 15% or higher, or a Critical risk with Unknown likelihood prevents High overall confidence.
4. Display High only when the weighted indicator is at least 1.5 and no safeguard applies.
5. Display Medium when the weighted indicator is at least 0.75 and no material-conflict safeguard applies.
6. Otherwise display Low.

Material assumptions and limitations affect the relevant dimension checks according to importance and impact. V1 does not subtract arbitrary points such as “minus 10 per assumption.”

### 18.12 Score explanation and ownership

Explanations are generated only after all deterministic outputs are available. They must state what strengthened the dimension, what weakened it, what is uncertain, and the exact computed result.

| Task | AI responsibility | Deterministic responsibility |
|---|---|---|
| Extract evidence | Extract structured facts, claims, and citations from sources. | Validate records, source IDs, and allowed fields. |
| Normalize analytical records | Summarize and classify with evidence links. | Validate schemas, references, and required coverage fields. |
| Classify score-input rubric level | Propose an allowed rubric level with rationale and counter-evidence. | Validate allowed values; reject unsupported or inconsistent classification. |
| Map rubric to numeric value | None. | Map fixed rubric levels to 0, 25, 50, 75, or 100. |
| Calculate input and dimension scores | None. | Apply fixed internal weights, availability rules, coverage caps, and essential-evidence caps. |
| Calculate weighted contribution and overall score | None. | Multiply fixed dimension scores by fixed overall weights, sum, and round. |
| Calculate confidence checks and labels | Assist with evidence classification where needed. | Apply check rules, confidence caps, cross-section safeguards, and aggregation rules. |
| Explain scores and confidence | Explain exact calculated values, evidence, counter-evidence, and uncertainty. | Supply authoritative values and prevent changing them. |
| Produce final verdict | Summarize under the future auditable verdict policy. | Supply score, confidence, risk, limitation, and validation-rule inputs. |

### Architectural Review

1. The seven dimensions are distinct enough: each has a defined owner, question, and double-counting boundary.
2. Weights total exactly 100%: 20 + 15 + 15 + 10 + 15 + 10 + 15.
3. Every dimension references defined upstream analytical records and shared evidence.
4. The LLM cannot directly assign a numeric dimension or overall score; it only proposes validated rubric levels.
5. Rubric mapping, weighting, caps, availability rules, contributions, and aggregation are deterministic.
6. Missing evidence is Unavailable, not negative evidence.
7. Thin evidence cannot silently produce extreme scores because coverage and essential-evidence caps apply.
8. Score describes attractiveness; confidence describes reliability. They remain separate labels and calculations.
9. Confidence is never a startup-success probability.
10. Source quality, directness, and independence matter as much as count; repeated sources do not create artificial confidence.
11. Material source conflicts remain visible and reduce confidence without fake averaging.
12. Assumptions and limitations affect dimension and report confidence according to materiality, not arbitrary point deductions.
13. Score caps are small, essential-evidence-based, and explainable.
14. Dimension unavailability prevents an overall numeric score; weights are never redistributed.
15. Overall calculation is reproducible from stored ScoreInputs, fixed weights, and the scoring version.
16. Risks map to their natural score dimension only; there is no extra universal penalty.
17. Recommended validation experiments do not change scores before they produce evidence.
18. FinalRecommendation consumes the assessment layer but cannot modify it.
19. Cross-section conflicts remain visible and lower confidence rather than being silently resolved.
20. `scoringVersion` and `confidenceVersion` make future rubric changes auditable.
21. The framework remains MVP-sized: seven dimensions, three or four fixed inputs per dimension, five numeric rubric anchors, a few caps, and three confidence labels.

## Decisions Finalized

1. **Dimension weights:** Problem Severity 20%; Customer Evidence 15%; Market Potential 15%; Growth / Trend Strength 10%; Competitive Opportunity 15%; Monetization Potential 10%; Execution Feasibility 15%.
2. **Internal scoring approach:** Hybrid rubric scoring. Analytical stages classify fixed inputs into Blocking/Weak/Moderate/Strong/Very strong; software maps them to 0/25/50/75/100 and applies fixed internal weights.
3. **Score bands:** 0–24 Weak; 25–44 Limited; 45–64 Moderate; 65–79 Promising; 80–100 Strong; plus Unavailable.
4. **Missing-data policy:** Unavailable inputs are excluded from the available-input mean, but weighted coverage applies transparent caps: 80+% none, 60–79% maximum 80, 40–59% maximum 65, below 40% dimension Unavailable.
5. **Dimension-unavailability policy:** If any of the seven dimensions is Unavailable, no numeric overall score is emitted and weights are never redistributed. A numeric score is Complete only when all dimensions have at least 60% coverage; it is Provisional when all are assessed but any dimension has 40–59% coverage.
6. **Essential-evidence caps:** Each dimension has one minimal, explainable cap preventing strong claims when essential direct evidence is absent.
7. **Confidence levels:** Display Low, Medium, or High only; no displayed numeric confidence or success probability.
8. **Confidence aggregation:** Dimension confidence uses required checks and caps. Overall confidence uses weighted dimension labels plus safeguards for material conflict, multiple critical Low-confidence dimensions, and Critical risks with Unknown likelihood.
9. **Score/confidence separation:** Attractiveness factors drive scores; quality, breadth, independence, agreement, recency, fit, assumptions, limitations, and conflicts drive confidence and coverage. Evidence quality is not double-penalized as a normal score factor.
10. **Deterministic/AI split:** AI extracts, classifies allowed rubric levels, and explains. Deterministic code validates, maps values, calculates scores, applies caps, aggregates confidence, and computes the overall result.

## What I Should Understand

The score is not an AI opinion dressed up as a number. It is a reproducible calculation over fixed inputs and weights. The judgment-heavy step is classifying evidence into a small rubric, and that classification stays auditable because it carries linked evidence, counter-evidence, assumptions, limitations, and rationale. Confidence then answers a separate question: how much should we trust the research basis for the score? Keeping those two outputs separate lets the product say, “This looks promising, but we do not yet know enough,” without pretending uncertainty is negative evidence.

## 19. Canonical Architectural Consistency Rules

The full conceptual model has been reviewed as one system. The following rules are authoritative wherever an earlier explanatory example is less specific.

### End-to-end flow

`ResearchRequest` → `StartupProfile` → source collection → `Source` → evidence extraction and normalization → `EvidenceItem` → branch analyses → cross-branch reconciliation → `ScoreInput` → `ScoreDimension` → `OpportunityScore` → `FinalRecommendation`.

`Assumption` and `Limitation` records can enter from any stage and remain visible through analysis, confidence, scoring caps, validation, and recommendation.

Problem and customer research may run in parallel. They first create independently identifiable pain-point and segment records. Cross-branch reconciliation then adds `affectedSegmentIds` and segment-to-pain-point links. This resolves the apparent dependency cycle without duplicating either model's data.

### Authoritative ownership

| Information | Authoritative owner | Other sections may do |
|---|---|---|
| Original founder input | ResearchRequest | Normalize or reference it. |
| Initial interpretation of the idea | StartupProfile | Use it to plan research; do not treat it as external evidence. |
| Source URL and publication metadata | Source | Reference the Source ID. |
| Reusable observed, derived, or inferred support | EvidenceItem | Reference the EvidenceItem ID. |
| Working choices caused by missing inputs | Assumption | Reference and validate them. |
| Research gaps and inaccessible or conflicting information | Limitation | Reference and explain their effect. |
| Problem-level pain, frequency, alternatives, and workaround burden | ProblemAnalysis | Add segment context without rescoring the pain. |
| Segments, customer roles, jobs, behavior, adoption, and customer payment signals | CustomerAnalysis | Reference these records for market, competitor, monetization, MVP, and validation analysis. |
| Market boundary, metrics, sizing, and trends | MarketAnalysis | Interpret them without copying figures. |
| Competitor facts and pricing | Competitor | Feed matrix, gap, and monetization analysis through IDs. |
| Deterministic comparison cells and metrics | CompetitorMatrix | Support gap and score inputs. |
| Customer-relevant differentiation hypotheses | CompetitiveGap | Feed MVP, risk, validation, and Competitive Opportunity. |
| Monetization candidates and payment-evidence interpretation | BusinessModel | Feed Monetization Potential and validation. |
| First product hypothesis and metric to observe | MVPRecommendation | Feed execution review and experiment design. |
| Material potential harm and its one natural scoring owner | Risk | Inform confidence, recommendation, and validation without adding a universal penalty. |
| Recommended experiment design | ValidationExperiment | Remain non-evidence until executed results are captured in a future model. |
| Numeric assessment | ScoreInput, ScoreDimension, OpportunityScore | Analytical sections supply inputs; AI explanation cannot alter the calculation. |
| Final action guidance | FinalRecommendation | Select and interpret existing records; introduce no new facts. |

### Classification and lineage

1. `Observed` means directly obtained from a source or explicitly supplied by the user.
2. `Derived` means calculated or normalized by a deterministic rule from recorded inputs.
3. `Inferred` means an AI-assisted interpretation grounded in linked evidence.
4. An `Assumed` proposition is owned by an Assumption record and is never stored as evidence. A consuming field may carry the working value only while referencing that Assumption.
5. `System metadata` identifies, versions, orders, or links records; it is not evidence.
6. Create an inferred EvidenceItem only when an insight must be reused across sections. A section-local interpretation stays in its owning analytical record and links its supporting evidence IDs.

### Reference and duplication rules

1. Every cross-model reference uses a globally unique, type-prefixed ID. Generic `relatedRecordIds` are valid because the prefix identifies the target type.
2. Raw URLs and source publication metadata exist only in Source. Entity records such as Competitor point to a `websiteSourceId`.
3. Derived and inferred evidence preserve lineage through `inputEvidenceIds`; observed evidence has at least one `sourceId`.
4. Parent-level `evidenceIds`, `assumptionIds`, and `limitationIds` are deduplicated indexes of records materially used anywhere in that parent. Child records keep the precise links needed to explain each finding.
5. Summary fields may compress existing information but may not create facts. Material summary statements retain `relatedRecordIds` and `evidenceIds`.

### Missing-data and partial-report rules

1. Missing evidence is `Unavailable` or `Unknown` according to the owning field; it is never automatically Low, zero, absent, or false.
2. An inaccessible page, thin sample, conflicting source, or failed branch creates a Limitation.
3. A necessary working choice creates an Assumption only when analysis must continue; otherwise the value remains Unknown or Unavailable.
4. Required top-level sections remain structurally present in a partial report. Their empty collections and unavailable values are explained by limitations and coverage metadata.
5. Scores use the coverage and essential-evidence policies in Section 18. Missing dimensions never cause weight redistribution.

### Scoring and confidence ownership

Each attractiveness factor has one score owner. Problem pain belongs to Problem Severity; customer behavior to Customer Evidence; market scale to Market Potential; momentum to Growth / Trend Strength; differentiation to Competitive Opportunity; payment evidence to Monetization Potential; and delivery blockers to Execution Feasibility. A risk maps to at most one of these dimensions through `scoreDimensionKey`.

Evidence quality, independence, directness, recency, agreement, assumptions, limitations, and research coverage primarily determine confidence and caps. They do not become extra attractiveness penalties. This keeps uncertainty separate from an unfavorable finding.

### Model-size review

The schema remains appropriate for an MVP research product. Its nested records exist where comparison, lineage, deterministic calculation, or cross-section reuse requires structure. Dashboard display choices, executed experiment results, database persistence, authentication, financial forecasting, and category-specific extensions remain outside this conceptual V1 contract.
